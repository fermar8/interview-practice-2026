# Relational Database Design and ACID Transactions

Scope: Schema design, transaction correctness, isolation, and performance foundations.

## How To Use This File In Interviews

Use this file to answer one core question clearly:

- How do you design a relational system that remains correct under concurrency and stays efficient as the data grows?

Interview goal:

- Show that you understand both correctness and operational trade-offs.
- Explain how transaction boundaries, normalization, indexes, and schema evolution work together.
- Demonstrate practical patterns, not textbook memorization.

High-signal answer pattern:

1. Start with the business invariant.
2. Explain the schema and constraints that enforce it.
3. Describe the transaction boundary and isolation level.
4. Show how indexes and query design avoid hot paths.
5. Mention migration and rollout safety.

## Why Relational Databases Still Matter [Axer Credit, Pluxee]

Relational databases are best when you need:

- Strong consistency and predictable updates.
- Clear relationships between entities.
- Enforcement of invariants with keys, constraints, and foreign keys.
- Transactions spanning multiple writes.

They are especially strong in domains like payments, inventory, identity, and internal operations where correctness matters more than flexible document shape.

Use a relational model when the write path is important and the product depends on data integrity. Use a document DB when shape changes frequently and you value flexibility over relational guarantees.

### Interview framing

- "A relational database is not just about tables; it is about modeling invariants and making them hard to violate."

## The Core Idea: SQL Is a Contract [Axer Credit, Pluxee]

A good relational design makes the database enforce rules, not just hold data.

Examples of critical invariants:

- A payment must either fully post or not post at all.
- A user cannot have duplicate active primary emails.
- An order line must reference a valid order.
- Inventory cannot go negative unless explicitly modeled as an allowed state.

These rules are enforced by:

- Primary keys
- Foreign keys
- Unique constraints
- Check constraints
- Transactions
- Application-level validation plus database-level safeguards

## ACID: The Mental Model [Axer Credit, Pluxee]

ACID is a concept for database correctness, not a guarantee that every implementation is perfect.

### Atomicity

All parts of a transaction succeed or none do.

Example for atomicity with a money transfer between accounts:
Explanation of the example:

- The transaction begins with `BEGIN;`.
- The first `UPDATE` deducts 100 from account 'A'.
- The second `UPDATE` adds 100 to account 'B'.
- If any part fails, the `COMMIT;` will not be reached, and the database will roll back to the state before `BEGIN;`, ensuring atomicity.

```sql
BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';

COMMIT;
```

If the second statement fails, the first must be rolled back.

This example demonstrates atomicity in action: either both updates succeed, or neither does. In a single database, atomicity is handled by the database engine using a transaction log, locking, and rollback semantics.

A realistic single-database transfer example:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 'A' AND balance >= 100;

UPDATE accounts
SET balance = balance + 100
WHERE id = 'B';

-- If either UPDATE fails, the transaction is rolled back automatically.
COMMIT;
```

What happens here:

- The transaction starts with `BEGIN;`.
- The debit on account A and the credit on account B are treated as one unit.
- If the debit fails because the balance is insufficient, or the second write fails due to a constraint or connection issue, the database rolls back the whole transaction.
- Only when both steps succeed does `COMMIT;` make the updates durable and visible.

The interview point is that atomicity is not just about writing two `UPDATE` statements; it is about treating them as one business action that cannot leave the system half-updated.

### In distributed systems, the problem is harder

When the debit and credit happen in different databases, services, or message queues, you can no longer rely on a single database transaction. In that case, atomicity typically requires coordination across multiple systems, and that coordination is expensive and failure-prone.

A common pattern is a two-phase commit (2PC):

1. Prepare phase: each participant agrees it can commit and records its intent.
2. Commit phase: a coordinator tells all participants to finalize the commit.

Conceptually:

```text
Coordinator                 Participant A                 Participant B
     |                           |                            |
     |-- prepare ---------------->|                            |
     |                           |-- prepare ---------------->|
     |<-- yes -------------------|                            |
     |                           |<-- yes -------------------|
     |-- commit ---------------->|                            |
     |                           |-- commit ---------------->|
     |                           |                            |
```

This works in theory, but it has major downsides:

- lock and coordination overhead
- coordinator failure during the prepare or commit phase
- blocking when one participant cannot commit
- complexity in recovery and replays

This is why most production systems avoid true distributed 2PC for normal app transactions and instead use patterns like:

- outbox tables with async workers
- saga orchestration / choreography
- idempotent retry logic
- ledger-style accounting records
- compensating transactions for business-level consistency

### Why teams avoid distributed 2PC

Distributed transactions are attractive on paper but painful in practice because they trade simplicity for coordination risk. A coordinator can fail, a participant can become unavailable, locks can be held too long, and recovery becomes extremely complex. In many systems, the true problem is not that the transaction is impossible; it is that the business process is too wide to be safely treated as one atomic unit.

The key design principle is often:

- keep the transactional boundary local to the system that owns the data
- treat cross-service behavior as eventually consistent or explicitly compensatable
- make each step safe to retry and safe to replay

### 1) Outbox tables with async workers

An outbox table is a local database table where the application writes an event before or alongside the business change. A background worker then publishes the event to Kafka, RabbitMQ, or another broker.

Example flow:

```sql
BEGIN;

INSERT INTO orders (id, user_id, total, status)
VALUES ('o-100', 'u-42', 4999, 'created');

INSERT INTO outbox_events (event_id, aggregate_type, aggregate_id, payload, created_at)
VALUES (gen_random_uuid(), 'Order', 'o-100', '{"type":"OrderCreated"}', NOW());

COMMIT;
```

Then a worker reads the outbox events and publishes them without putting the main transactional flow at risk. 
When retries are needed, they only affect the worker and not the original transaction.

Why this is used:

- the database commit is the source of truth
- the external side effect is retried independently
- the app does not need a distributed transaction across DB and message broker
- the design is easier to recover after crashes and restarts

Interview framing:

- "The outbox pattern turns an unreliable external side effect into an internal, replayable event stream."

### 2) Saga orchestration and choreography

A saga breaks a long-running workflow into smaller steps that can each succeed or fail independently, with explicit recovery logic.

#### Orchestration

A coordinator tells each service what to do in sequence.

```text
Create payment -> reserve inventory -> create order -> send email
```

If reserve inventory fails, the orchestrator can issue a compensation step such as reversing the payment or cancelling order creation.

#### Choreography

Each service reacts to events from others without a central coordinator.

```text
OrderCreated -> InventoryReserved -> PaymentCaptured -> EmailSent
```

This is often more flexible, but harder to reason about when debugging a broken flow.

The important interview point is:

- "A saga is not 'no transaction'; it is 'explicit compensation and retry semantics instead of one giant atomic block.'"

### 3) Idempotent retry logic

In distributed systems, retries happen. A message can be delivered more than once, a request can time out after the server processed it, or a worker can crash after writing part of the result.

This is why the operation must be idempotent.

Example:

```sql
INSERT INTO payments (payment_id, user_id, amount, status)
VALUES ('p-123', 'u-42', 5000, 'captured')
ON CONFLICT (payment_id) DO NOTHING;
```

The same payment request can be retried safely because it will not duplicate the row or double-charge the account when guarded by a unique idempotency key.

Why it matters:

- retries are inevitable
- exactly-once delivery is usually a myth in distributed delivery systems
- idempotency gives you correctness in the face of retries

### 4) Ledger-style accounting records

In finance and accounting, it is common to record immutable journal entries instead of mutating a single balance in place.

Example ledger entry concept:

```sql
INSERT INTO ledger_entries (
  entry_id,
  account_id,
  direction,
  amount_cents,
  reference_id,
  created_at
)
VALUES (
  'e-001',
  'A',
  'debit',
  10000,
  'txn-42',
  NOW()
);
```

Then the balance is derived from the sum of ledger entries, or a derived table is maintained carefully.

Why this matters:

- you preserve an audit trail
- you can reconcile transactions later
- you can recover from partial failures more cleanly
- you avoid hidden data loss from overwriting a single mutable balance

This is often more robust than implementing the entire business rule as a single `UPDATE accounts SET balance = ...` with fragile locking assumptions.

### 5) Compensating transactions for business-level consistency

A compensating transaction reverses the effect of a previous action when later steps fail.

Example:

- create subscription
- charge card
- send welcome email
- later email fails
- compensate by refunding the card or flagging the subscription for manual review

This is especially common when a step is non-transactional by nature, such as:

- sending an email
- invoking a third-party payment provider
- publishing a message to a queue
- calling an external notification service

The key difference is that compensation is business-aware and usually not a database rollback. It is a way of making the final state acceptable even when the full workflow could not be atomic.

### Interview answer to use

- "For distributed systems, I usually prefer local atomicity plus explicit recovery semantics over a broad two-phase commit. The goal is not to pretend all steps are in one transaction; the goal is to make every step safe, retryable, and recoverable."

### Real-world takeaway

Distributed atomicity is expensive, fragile, and often operationally unacceptable for normal application flows. The best systems usually do one of these:

- keep the transaction inside a single database boundary whenever possible
- separate the critical state update from external effects
- use event-driven message patterns with durable outbox processing
- define idempotent operations and replay-safe business logic
- design compensation or reconciliation instead of pretending a global transaction exists

This is why the right answer in interviews is rarely "use 2PC everywhere." The better answer is: "I choose the smallest transaction boundary that preserves correctness, and I add explicit recovery patterns for cross-system work."

A common SQL-style example of a prepared transaction is not the normal application pattern and is often database-specific. It is more of a recovery/coordination primitive than a typical application transaction:

```sql
-- PostgreSQL-style prepared transaction flow (database-specific)
BEGIN;
-- write local state
PREPARE TRANSACTION 'txn1';

-- later, after coordinator decides it is safe to finalize
COMMIT PREPARED 'txn1';
```

This is not the same as a simple application-level `BEGIN ... COMMIT` in one relational database. It is a specialized mechanism for transaction coordination and recovery in distributed or clustered database scenarios.

### Consistency

The database transitions from one valid state to another valid state.

Example for consistency with business invariants:

- `balance >= 0` is a business invariant.
- `order_total` should match the sum of its line items.

The database cannot guarantee business meaning by itself; it helps enforce the rules you encode in schema and logic.
We maintain consistency by ensuring that all business rules and invariants are respected within each transaction.

### Isolation

Transactions do not interfere with each other in unintended ways.

This is where the interesting interview questions begin. The default isolation level is often not enough for correctness-sensitive code.
For example, if two transactions try to update the same row simultaneously, isolation ensures that one transaction's changes are not visible to the other until committed.
This prevents phenomena like dirty reads, non-repeatable reads, and phantom reads, depending on the isolation level chosen.
An example of isolation issues is the "lost update" problem, where two transactions read the same value and then update it, causing one update to overwrite the other.
To prevent lost updates, proper isolation levels and techniques like optimistic or pessimistic locking should be used.

Optimistic locking assumes conflicts are rare and checks for conflicts before committing.
An example of optimistic locking is using a version number or timestamp to detect if the data has been modified by another transaction before committing.
Working example:

```sql
-- Optimistic locking example
BEGIN;
SELECT balance, version FROM accounts WHERE id = 1;
-- Application logic to update balance
UPDATE accounts SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = <previous_version>;
COMMIT;
```

Pessimistic locking assumes conflicts are likely and locks resources early to prevent conflicts.
An example of pessimistic locking is acquiring a row-level lock before reading and updating a row, ensuring no other transaction can modify it until the lock is released.
Working example:

```sql
-- Pessimistic locking example
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- Application logic to update balance
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

### Durability

Once committed, data should survive failures, usually by writing to stable storage and using WAL/redo logs or equivalent durable storage.
This is typically achieved through mechanisms like write-ahead logging (WAL) or redo logs, ensuring that once a transaction is committed, its changes are durable even in the event of a crash.
A working example would be using a database that supports WAL, such as PostgreSQL, where changes are first written to the WAL before being applied to the main data files. This ensures that even if the system crashes immediately after a commit, the changes can be recovered from the WAL.

## Transaction Boundaries: Where Correctness Begins [Axer Credit, Pluxee]

The key question is not "Should I use a transaction?" but "What is the business unit of work?"

Examples:

- Transfer money between accounts: one transaction.
- Place an order: may require inventory reservation, payment, and ledger updates as one logical unit.
- Send a welcome email: should not usually be inside the payment transaction; it is a side effect and should be handled asynchronously or after commit.

### Good interview rule

- Keep the transaction as small as possible while still covering the atomic business unit.
- Do not hold locks for long-running external calls.
- Avoid mixing business logic with side-effecting work inside a database transaction if that work can fail separately.

## Isolation Levels [Axer Credit, Pluxee]

### Read Uncommitted

It is rarely useful in production and often not fully supported consistently.

- Can read uncommitted data from other transactions.
- Poor for correctness-sensitive systems.

### Read Committed

The default in many systems.

- Prevents dirty reads.
- A transaction sees only committed rows.
- Repeated reads in the same transaction may still see different data if another transaction commits in between.

### Repeatable Read

Common in systems that need stable reads within a transaction.

- Prevents non-repeatable reads.
- Usually guarantees a snapshot for the transaction.

Important caveat:

- It does not always mean "serializable" behavior in the strictest sense.
- You can still get phantom reads depending on database semantics.

### Serializable

Strongest isolation.

- Makes transactions behave as if they were executed one after another.
- More locking or conflict detection.
- Higher contention and lower throughput.

Use it when correctness matters more than throughput, such as inventory reservation, seat booking, or ledger reconciliation.

### Interview answer pattern

- "I choose the isolation level based on the invariant being protected. If the business rule is 'only one user may reserve this seat,' I need stronger guarantees than a simple read committed transaction."

## Row-Level Locks, Deadlocks, and Contention [Axer Credit, Pluxee]

### Row-Level Locks

Most relational databases lock rows or index entries during writes.

Example:

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 'A';
```

If two transactions update the same row simultaneously, one waits or gets a lock conflict.

### Deadlocks

Deadlocks happen when transactions hold locks in different orders.

Example:

- Transaction 1 locks A then B.
- Transaction 2 locks B then A.
- Both wait forever unless one is aborted.

### How to reduce deadlocks

- Keep transactions short.
- Lock rows in a stable order.
- Avoid user interaction inside transactions.
- Batch updates carefully.
- Retry transient deadlock errors with bounded backoff.

### Retry strategies

A good pattern is:

- Retry only on deadlock/serialization/transient lock errors.
- Keep retries bounded.
- Do not retry non-idempotent side effects blindly.

Example interview idea:

- "A payment retry is safe only if the operation is idempotent or guarded by a payment ID / idempotency key."

## Relational Modeling: Normalization and Relationships [Axer Credit, Pluxee]

### One-to-many

A user has many orders.

```sql
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email TEXT NOT NULL UNIQUE
);

CREATE TABLE orders (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### Many-to-many

A user can belong to many groups, and a group can contain many users.

```sql
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  name TEXT NOT NULL
);

CREATE TABLE groups (
  id BIGSERIAL PRIMARY KEY,
  name TEXT NOT NULL
);

CREATE TABLE user_groups (
  user_id BIGINT NOT NULL REFERENCES users(id),
  group_id BIGINT NOT NULL REFERENCES groups(id),
  PRIMARY KEY (user_id, group_id)
);
```

### Why normalization matters

Normalization reduces duplication and makes the model easier to reason about.

At the same time, denormalization may be useful for read-heavy workloads or reporting, but only when you understand the trade-off.

### Interview line

- "I do not denormalize just to optimize a query until I know whether the bottleneck is read latency, write amplification, or a wrong index strategy."

## Constraints and Data Integrity [Axer Credit, Pluxee]

Database constraints are one of the most important safeguards.

Use:

- `PRIMARY KEY` for identity and uniqueness
- `FOREIGN KEY` for relationships
- `UNIQUE` to prevent duplicate business values
- `CHECK` to enforce domain rules
- `NOT NULL` to prevent invalid emptiness

Example:

```sql
CREATE TABLE accounts (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id),
  balance NUMERIC(18, 2) NOT NULL CHECK (balance >= 0),
  currency CHAR(3) NOT NULL,
  UNIQUE (user_id, currency)
);
```

This is much stronger than trusting application code alone.

## Indexes and Query Plans [Axer Credit, Pluxee]

### Why indexes matter

Without good indexes, relational databases become slow even when the schema is correct.

Example:

```sql
CREATE INDEX idx_orders_user_created
ON orders (user_id, created_at DESC);
```

This helps when the app asks:

```sql
SELECT *
FROM orders
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

### What interviewers care about

- The difference between a clustered index and a secondary index
- When a `WHERE` clause is selective enough to justify an index
- Why too many indexes hurt writes and storage
- How to use `EXPLAIN` for query plan validation

### Good guideline

- Index the columns used in filters, joins, and sort order.
- Prefer composite indexes that match actual query patterns.
- Avoid indexing every column indiscriminately.

## Pagination, Filtering, and Sorting [Axer Credit, Pluxee]

Efficient APIs must paginate and order data predictably.

Example:

```sql
SELECT *
FROM orders
WHERE user_id = 42
  AND created_at >= NOW() - INTERVAL '30 days'
ORDER BY created_at DESC
LIMIT 20
OFFSET 40;
```

Key issues:

- `OFFSET` becomes expensive at large page numbers.
- Use keyset pagination where possible for high-cardinality feeds.
- Sorting should align with index order.
- Filtering on unindexed or high-cardinality columns can degrade performance.

### Interview-quality answer

- "I prefer index-friendly pagination patterns because they scale better than scanning large offset ranges."

## Schema Migrations and Backward-Compatible Deployments [Axer Credit, Pluxee]

Database changes are operational changes.

### Common migration patterns

- Add column, then backfill, then use it.
- Add index concurrently where supported.
- Do not drop constraints or columns in a way that breaks active traffic.
- Prefer additive changes over destructive ones.

Example sequence:

```sql
ALTER TABLE users ADD COLUMN last_login_at TIMESTAMPTZ;
CREATE INDEX CONCURRENTLY idx_users_last_login_at ON users (last_login_at);
```

Then later:

- backfill existing rows,
- update application code,
- enable usage,
- clean up only when safe.

### Why it matters

Schema changes often happen while application traffic is still live. A migration that is unsafe under concurrency can cause downtime or incorrect reads.

## Monetary Precision: Do Not Use Float [Axer Credit, Pluxee]

For money, do not rely on floating-point numbers.

Bad:

```sql
balance DOUBLE PRECISION
```

Good:

```sql
balance NUMERIC(18, 2)
```

Or store minor units as integer cents:

```sql
balance_cents BIGINT NOT NULL
```

### Why

- Floating-point arithmetic introduces rounding errors.
- Monetary totals need exact representation.
- Ledger systems often require exact accounting semantics.

### Strong interview answer

- "For financial systems, exactness is a correctness requirement, not a convenience feature."

## Connection Pools and Transaction Performance [Axer Credit, Pluxee]

A database can be correct but still perform badly if the app uses too many connections or holds transactions too long.

### Typical concerns

- Max pool size and connection starvation
- Long-lived transactions that block other work
- Opening transactions around large reads or user input delays
- Reusing connections without good timeout boundaries

### Good pattern

- Keep transactions short.
- Do not open a transaction just to read a single row.
- Close resources promptly.
- Tune the pool based on concurrency and actual throughput.

## When To Use Relational Databases [Axer Credit, Pluxee]

Choose relational when:

- The data model is stable and structured.
- You need strong consistency and constraints.
- Transactions represent real business units of work.
- You need joins, reporting, and rich analytical queries.

Choose document or key-value systems when:

- The schema changes often.
- The workload is mostly append-heavy and document-centric.
- ACID consistency is less critical than flexibility.

The key is not dogma; it is matching the storage model to the correctness requirement.

## Ledgers [Axer Credit, Pluxee]

Ledgers are specialized tables or systems used to track financial transactions in a way that ensures immutability and auditability.
A way to implement a ledger is to have a table where each row represents a financial transaction, and the table is only ever appended to. Updates to existing rows are avoided to maintain immutability.

### Key characteristics

- Each entry represents a discrete financial event.
- Entries are append-only; updates are rare and usually involve creating a compensating entry.
- Balances are derived from summing the relevant entries rather than storing a mutable balance.

### Why

- Ensures a clear audit trail.
- Reduces the risk of accidental or malicious data corruption.
- Aligns with accounting principles like double-entry bookkeeping.

## Deep Mock Questions Focused On This File

### 1) "What is the difference between atomicity and consistency in ACID?"

Strong answer:

- Atomicity is about transaction all-or-nothing behavior.
- Consistency is about moving from one valid state to another valid state.
- The database enforces the mechanics; your schema and invariant design define the validity.

### 2) "When would you choose Serializable over Read Committed?"

Strong answer:

- When the business rule depends on preventing anomalies across concurrent transactions.
- Typical examples: seat booking, inventory reservation, financial ledger updates.
- The trade-off is higher contention and lower throughput.

### 3) "How do you prevent deadlocks in a transaction-heavy system?"

Strong answer:

- Keep transactions short.
- Lock rows in a consistent order.
- Avoid broad transactions.
- Retry deadlock/serialization errors with bounded backoff.

### 4) "Why is `NUMERIC(18, 2)` or integer minor units better than floats for money?"

Strong answer:

- Exact representation matters in accounting.
- Floating-point introduces rounding error.
- Money is usually a correctness issue, not a performance issue.

### 5) "What is the role of indexes in relational correctness and performance?"

Strong answer:

- Indexes support efficient lookups and join order.
- They improve query latency.
- But too many indexes increase write cost and can affect update performance.
- The right index is driven by actual query patterns, not by theory alone.

### 6) "Why are foreign keys and constraints important if the application already validates request data?"

Strong answer:

- Application validation is not enough because multiple code paths can write data.
- Constraints enforce rules at the database boundary.
- They reduce silent corruption and improve safety in multi-service environments.

### 7) "What does a good migration strategy look like for a live system?"

Strong answer:

- Additive changes first.
- Backfill or validate data safely.
- Deploy application logic that reads the new shape.
- Then switch traffic gradually, with rollback readiness.

### 8) "How do you decide whether a query needs pagination or keyset pagination?"

Strong answer:

- Use offset pagination for small result sets or administrative screens.
- Use keyset pagination for large event or feed-style queries.
- Keyset pagination is usually better for scrollable APIs because it avoids large offset scans.

## Common Mistakes To Avoid

- Treating transactions as a blanket solution for all bugs.
- Holding database transactions open while waiting on external APIs.
- Using floats for money.
- Adding indexes without measuring actual query patterns.
- Forgetting about deadlock and serialization handling in concurrent workloads.
- Using broad transactions when a narrower business boundary is enough.
- Deploying destructive migrations without a safe rollback plan.

## 60-Second Interview Summary

"I think about relational databases as systems for enforcing business invariants. The real value is not just storing rows; it is making correctness explicit through keys, constraints, isolation, and transactions. For critical operations, I choose transaction boundaries carefully, use appropriate isolation levels, guard against deadlocks, index for actual query patterns, and design schema changes to be safe during live deployment. When money or order correctness matters, exact arithmetic and transaction discipline are non-negotiable."
