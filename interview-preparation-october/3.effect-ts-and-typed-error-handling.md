# Effect-TS and Typed Error Handling

Scope: Explicit dependency and error modeling for composable async systems.

## How To Use This File In Interviews

Use this file to answer one core question clearly:

- Why would a team adopt Effect-TS instead of plain async/await plus exceptions?

Interview goal:

- Show that you understand the trade-off between explicitness and complexity.
- Explain how Effect improves correctness and testability in async systems.
- Demonstrate practical patterns, not library trivia.

High-signal answer pattern:

1. Describe the problem in plain Node.js/TypeScript.
2. Show what Effect makes explicit (errors, dependencies, interruption).
3. Explain why that matters in production.
4. Mention one cost (learning curve, ceremony, ecosystem fit).

## Why Teams Choose Effect-TS [AppFire]

Effect-TS is useful when a codebase has:

- Multiple external dependencies (DB, providers, queues).
- Complex async flows with retries/timeouts/cancellation.
- A need for reliable, typed error channels.
- A strong requirement for deterministic tests.

Plain async/await pain points:

- Exceptions are implicit and often undocumented.
- Dependency wiring is spread across modules.
- Retrying/timeout logic gets duplicated.
- Cancellation and cleanup are easy to miss.

Effect value proposition:

- Errors are explicit in the type.
- Required dependencies are explicit in the type.
- Effects compose predictably.
- Resource lifecycle is modeled, not ad-hoc.

## Typed Error Handling (Core Value) [Axer Credit, AppFire]

### The Concept

In Effect, failure is part of the type, not only runtime behavior.

Strong interview phrasing:

- "I can read an effect type and know what can fail and what dependencies are required."

### Example

```ts
import { Effect } from "effect";

type UserNotFound = { _tag: "UserNotFound"; userId: string };
type DatabaseError = { _tag: "DatabaseError"; message: string };

type User = { id: string; email: string };

const findUser = (
  userId: string,
): Effect.Effect<User, UserNotFound | DatabaseError> =>
  userId === "missing"
    ? Effect.fail({ _tag: "UserNotFound", userId })
    : Effect.succeed({ id: userId, email: "user@example.com" });
```

Why this is powerful:

- Callers must handle both `UserNotFound` and `DatabaseError` paths.
- Failure behavior is visible at compile time.

### Interview Follow-Up You Should Handle

Q: "Do typed errors remove all runtime failures?"
A: "No. They improve expected error modeling. Unknown defects can still exist, but typed channels reduce accidental unhandled cases in core flows."

## Effect, Context, and Layer [AppFire]

### Effect

`Effect<A, E, R>` means:

- `A`: success value
- `E`: error type
- `R`: required environment/dependencies

It is used to model asynchronous computations with explicit success, error, and dependency types.

Interview-quality line:

- "Effect makes data, errors, and dependencies first-class in the function signature."

```ts
// Example of an Effect type
const exampleEffect: Effect.Effect<string, Error, number> = Effect.succeed(42);
// handling errors:
const handledEffect = exampleEffect.catchAll((error) =>
  Effect.succeed(`Handled error: ${error.message}`),
);
// dependencies:
const dependencyEffect: Effect.Effect<string, Error, { config: string }> =
  Effect.succeed({ config: "configValue" });
```

### Context

Context is a typed dependency container. It allows you to define and access services in a type-safe manner throughout your application.

Use it to define service contracts:

```ts
import { Context } from "effect";

interface EmailService {
  sendWelcome(email: string): Promise<void>;
}

class EmailServiceTag extends Context.Tag("EmailService")<
  EmailServiceTag,
  EmailService
>() {}
```

### Layer

Layer provides concrete implementations for dependencies. Which means you can swap implementations without changing the dependent code.

```ts
import { Layer } from "effect";

const LiveEmailLayer = Layer.succeed(EmailServiceTag, {
  sendWelcome: async (email: string) => {
    console.log("sending welcome email to", email);
  },
});
```

Why this matters:

- Dependency wiring is centralized and composable.
- Swapping test/live implementations is explicit and safe.

## Dependency Injection With Explicit Contracts [Axer Credit, AppFire]

### Practical Service Composition

```ts
import { Effect } from "effect";

const registerUser = (email: string) =>
  Effect.gen(function* () {
    const emailService = yield* EmailServiceTag;
    // Domain steps could include repository calls and validation
    yield* Effect.tryPromise(() => emailService.sendWelcome(email));
    return { ok: true as const };
  });
```

Interview framing:

- "Instead of importing globals directly, I request dependencies via context. This improves modularity and testability."

## Composing Asynchronous Operations [Axer Credit, Pluxee, AppFire]

### Why Composition Is Cleaner

Effect composition helps avoid deeply nested `try/catch` and inconsistent retry behavior.

Useful composition patterns:

- Sequential dependent steps.
- Parallel independent steps.
- Explicit fallback/recovery paths.

```ts
import { Effect } from "effect";

const fetchProfile = Effect.succeed({ id: "u1", name: "Ana" });
const fetchInvoices = Effect.succeed([{ id: "i1", total: 1200 }]);

const loadDashboard = Effect.all({
  profile: fetchProfile,
  invoices: fetchInvoices,
});
```

What to say in interviews:

- "Composition keeps control flow explicit and makes failure behavior uniform across steps."

## Resource Safety And Cleanup [AppFire]

### Why It Matters

Leaked connections and unfinished cleanup are common production issues.

Effect supports resource-safe patterns where acquire/use/release is explicit.

```ts
import { Effect } from "effect";

type FakeConn = { close: () => Promise<void> };

const acquireConn = Effect.succeed<FakeConn>({
  close: async () => {
    console.log("connection closed");
  },
});

const useConn = (conn: FakeConn) =>
  Effect.succeed(`using connection: ${Boolean(conn)}`);

const releaseConn = (conn: FakeConn) => Effect.tryPromise(() => conn.close());

const program = Effect.acquireUseRelease(acquireConn, useConn, releaseConn);
```

Interview-quality line:

- "Even on failure or interruption, release still runs. That is a major reliability win."

## Retries, Timeouts, and Interruption [Axer Credit, Pluxee, AppFire]

### Why This Section Is High Signal

Most real incidents involve unstable dependencies. Interviewers look for practical resilience patterns.

Patterns to mention:

- Timeout boundaries on remote calls.
- Retry only transient failures.
- Avoid infinite retries.
- Respect cancellation/interruption.

Example shape:

```ts
import { Duration, Effect, Schedule } from "effect";

const unstableCall = Effect.tryPromise(async () => {
  // pretend remote call
  return "ok";
});

const resilientCall = unstableCall.pipe(
  Effect.timeout(Duration.seconds(2)),
  Effect.retry(Schedule.recurs(3)),
);
```

Strong interview caveat:

- "Retry policy must be scoped to idempotent operations or guarded by idempotency keys."

## Routing and HTTP Integration [Axer Credit, Pluxee, AppFire]

### Why This Section Is High Signal

Routing and HTTP integration are common in real-world applications. Interviewers want to see that you can connect your business logic to web frameworks while maintaining testability and resilience.

- Detailed example with routing:

```ts
import { Effect, Layer } from "effect";
import { createServer } from "http";

const AppLayer = Layer.succeed(AppServiceTag, {
  handleRequest: async (req: Request) => {
    return new Response("Hello World");
  },
});

const server = createServer((req, res) => {
  Effect.provideLayer(AppLayer)(
    Effect.succeed(req).pipe(
      Effect.flatMap((req) => AppServiceTag.read().handleRequest(req)),
    ),
  ).then(
    (response) => {
      res.writeHead(200, { "Content-Type": "text/plain" });
      res.end(response.body);
    },
    (error) => {
      res.writeHead(500, { "Content-Type": "text/plain" });
      res.end(`Error: ${error.message}`);
    },
  );
});

server.listen(3000);
console.log("Server is listening on http://localhost:3000");

// Example route addition
server.on("request", (req, res) => {
  if (req.url === "/health") {
    res.writeHead(200, { "Content-Type": "text/plain" });
    res.end("OK");
  }
});
```

Interview line:

- "I can run the same business effect with live or test layers, so tests focus on behavior rather than framework plumbing."

## Deep Mock Questions Focused On This File [AppFire, Axer Credit, Pluxee]

### 1) "Why use Effect-TS instead of async/await and try/catch?"

Strong answer:

- Async/await is great for simple flows.
- Effect becomes valuable when you need explicit typed errors, explicit dependency requirements, and reusable resilience policies.
- The trade-off is more abstraction and onboarding cost.

### 2) "What does Effect's type signature buy you in large teams?"

Strong answer:

- It documents success, failure, and dependency requirements in code.
- It reduces hidden coupling and surprise runtime failures.
- It improves refactoring confidence across teams.

### 3) "How do Context and Layer differ from classic DI containers?"

Strong answer:

- Similar goal (dependency provisioning), but Effect keeps dependency requirements in effect types.
- Layers compose functionally and are easy to swap in tests.
- Wiring becomes explicit rather than magic runtime lookup.

### 4) "How do you avoid overusing Effect for trivial logic?"

Strong answer:

- Keep pure logic as plain functions.
- Use Effect at boundaries where async, errors, dependencies, or resource safety matter.
- Avoid ceremony for tiny utility code.

### 5) "What is the biggest production benefit of typed errors?"

Strong answer:

- Predictable failure handling paths.
- Safer API mapping and alerting.
- Fewer hidden throw paths in critical flows.

### 6) "How do retries/timeouts interact with business correctness?"

Strong answer:

- Technical resilience is not enough; business safety matters.
- Retries must be bounded and tied to idempotency semantics.
- Timeouts should trigger explicit compensation or verification workflows when needed.

### 7) "How do you test Effect services without real infrastructure?"

Strong answer:

- Replace live layers with test layers.
- Assert on business outcomes and typed errors.
- Keep integration tests for adapter boundaries only.

### 8) "What are valid concerns against adopting Effect-TS?"

Strong answer:

- Learning curve and initial velocity dip.
- More abstraction may be unnecessary in small/simple services.
- Team success depends on shared conventions and disciplined usage.

## Common Mistakes To Avoid

- Treating Effect as a mandatory replacement for every function.
- Modeling all failures as generic strings.
- Retrying non-idempotent operations without guards.
- Hiding dependencies instead of expressing them in Context/Layer.
- Ignoring the cost of abstraction in small codepaths.

## 60-Second Interview Summary

"I use Effect-TS when explicitness is worth the cost: typed errors, explicit dependencies, and structured async composition. Effect, Context, and Layer make control flow and wiring predictable, while resource-safe patterns and built-in timeout/retry composition improve reliability. I still keep simple logic plain TypeScript and apply Effect where it materially improves correctness, testability, and operability."
