# System Design: Service Boundaries and Cloud Performance

Scope: how to split responsibilities between services, define stable contracts, and keep a cloud system performant and resilient without over-engineering the architecture.

## How To Use This File In Interviews

Use this file when the interviewer asks:

- "How do you decide where to split a system into services?"
- "When is a modular monolith better than microservices?"
- "How do you design a stable API contract across teams?"
- "Why is caching not just a performance trick but a consistency trade-off?"
- "How do you keep a production system from failing under load?"

## Why Service Boundaries Matter [Axer Credit, Pluxee, AppFire]

A bad service boundary creates many downstream problems:

- duplicate logic across teams
- data ownership confusion
- hidden coupling and fragile deployments
- local fixes that cause global outages
- expensive cross-service calls under load

A good boundary is usually defined by:

- clear ownership
- stable business capabilities
- well-defined data ownership
- manageable failure modes
- explicit contracts between systems

The goal is not to maximize the number of services. The goal is to create a system that is understandable, debuggable, and resilient.

## Modular Monoliths vs Microservices [Axer Credit, Pluxee, AppFire]

This is one of the most common architecture questions in interviews.

### Modular monolith

A modular monolith keeps one deployable application, but organizes code into modules with clear responsibilities.

Examples of modules:

- billing
- orders
- inventory
- notifications
- user management

Advantages:

- simpler deploys and debugging
- easier to reason about transactions
- lower operational overhead
- faster to build and iterate in early stages

Disadvantages:

- can become a “big ball of mud” if boundaries are unclear
- scaling a single module is harder than scaling an individual service
- team coordination becomes difficult as the codebase grows

A modular monolith is often the correct choice when:

- the product is still evolving rapidly
- the team is small or mid-sized
- most problems are not yet caused by service-to-service complexity

### Microservices

Microservices split the application into independently deployable services.

Advantages:

- independent scaling and deployment
- better isolation of failures when boundaries are well-designed
- clearer ownership by domain
- easier to scale specific hot paths

Disadvantages:

- higher operational complexity
- more network calls and failure modes
- harder debugging across services
- more difficult data consistency guarantees

Microservices are often justified when:

- teams are large and independent
- there are very different scaling profiles per domain
- the system has strong domain boundaries and clear ownership
- the organization is ready for distributed system operations

### Common interview answer

A strong answer is usually along these lines:

- start with a modular monolith if the domain is not yet stable
- define service boundaries by business capability and data ownership
- split only when the operational and organizational benefits outweigh the complexity cost

This is often more mature than “we should always do microservices.”

## Service Boundaries: The Real Design Principle [Axer Credit, Pluxee, AppFire]

The best boundary is not based on technical convenience alone. It is based on business capability and ownership.

### Good boundaries

A good boundary usually resembles something like:

- checkout service owns payment intent and fulfillment decisions
- inventory service owns stock and reservation state
- billing service owns invoices and ledger accounting

These services make decisions around their own domain and expose clear contracts.

### Bad boundaries

Bad boundaries often happen when teams split by technical layer instead of business domain.

Examples:

- one service for controllers, one for repositories, one for DTOs
- separate services for each database table
- services built around deployment concerns instead of business needs

This leads to chatty systems and unclear ownership.

### Data ownership

The strongest architectural decisions usually come from one principle:

- one service owns one source of truth for a domain entity

For example:

- orders service owns order state
- inventory service owns stock reservations
- notifications service does not own the order itself

If multiple services share the same data without clear ownership, the system becomes inconsistent and fragile.

## API Contracts: Stability, Compatibility, and Change Management [Axer Credit, Pluxee, AppFire]

An API contract defines what a service promises to clients.

Good contracts include:

- request/response shape
- validation rules
- versioning rules
- error semantics
- retry and timeout expectations
- compatibility guarantees

### Backward compatibility

A service should avoid breaking clients silently.

Common strategies:

- additive changes only
- optional fields instead of removing required fields
- versioned endpoints or media types
- explicit deprecation windows
- consumer-driven contract tests

### Breaking changes

A breaking change is a serious operational decision because it can cause partial outages across the system.

Examples of breaking changes:

- changing a field type from string to number
- removing fields required by clients
- changing the meaning of a status code
- changing the semantics of an idempotent operation

Strong teams do not just ship a new API and hope for the best. They test compatibility and communicate migration plans.

### Contract testing

Contracts should be tested as a system property, not just as local unit tests.

This includes:

- consumer expectations for response schemas
- provider guarantees
- explicit error handling behavior
- compatibility with older clients

The best service boundaries reduce the need for unrelated clients to know implementation details.

## Caching and Invalidation: Performance vs Correctness [Axer Credit, Pluxee, AppFire]

Caching is not just “speed.” It is a consistency decision.

### Cache-aside pattern

The app checks cache first, then falls back to the database.

Advantages:

- simple to implement
- works well for read-heavy workloads
- reduces repeated DB load

Disadvantages:

- cache stampede risk
- stale data if invalidation is not explicit
- complexity when updates happen frequently

### Write-through and write-back

These may be useful for some workloads, but they require more careful consistency reasoning.

Write-through updates the cache when the DB changes.

Write-back defers cache updates and can create more risk if the system fails.

### Invalidation strategy

This is where many systems fail.

Common invalidation mistakes:

- cache keys not namespaced properly
- invalidating too broadly
- stale negative caching
- caches updated without the correct tenant or resource context

A strong answer usually says:

- cache only data with a clear invalidation model
- avoid caching highly dynamic or security-sensitive state
- set TTLs intentionally
- use versioned keys for large invalidation events

### The real performance question

The correct question is not “should we cache?” It is:

- what data is expensive to fetch?
- how stale can it be?
- who owns invalidation?
- what happens if the cache is wrong?

## Performance Profiling: Where Bottlenecks Actually Live [Axer Credit, Pluxee, AppFire]

A common interview mistake is to jump straight to adding cache or scaling out without identifying the actual bottleneck.

### Database profiling

Look for:

- slow queries
- missing indexes
- lock contention
- large result sets
- N+1 queries
- expensive joins

A slow API often has a small number of expensive database calls rather than a large number of trivial ones.

### Application profiling

Look for:

- CPU hotspots
- memory bloat
- excessive object creation
- repeated serialization work
- network call fan-out

The problem is often not the database alone but the number of application-level operations done per request.

### Observability before optimization

Do not optimize by intuition. Measure.

A mature answer includes:

- baseline p50/p95 latency
- queue depth and saturation
- DB CPU and connection saturation
- hot endpoints and top queries
- user-impacting error rates

This is where system design and engineering discipline meet.

## Rate Limiting, Resource Exhaustion, and Resilience [Axer Credit, Pluxee, AppFire]

If a system is not built to fail gracefully, it will fail with more noise and more user impact.

### Rate limiting

Rate limiting protects shared infrastructure and prevents one consumer from exhausting resources.

Examples:

- per-user API quotas
- per-tenant limits. The definition of a tenant is context-dependent and could be an organization, account, or customer group.
- per-IP protection for public endpoints
- queue consumer concurrency caps

You can rate limit by:

- requests per second
- tokens or leaky buckets
- quotas by business account
- weighted requests by operation cost

### Resource exhaustion

A system can fail not only because of CPU or memory, but because of:

- DB connection exhaustion
- thread pool starvation
- disk fill-up
- queue backlog growth
- external API retry storms

The design needs to anticipate saturation and fail safely.

### Circuit breakers and graceful degradation

If a dependency starts failing repeatedly, the system should stop blindly retrying it.

Patterns include:

- circuit breaker pattern
- fallback responses
- degraded reads or cached data
- partial service availability

This matters because a healthy system does not escalate an already failing dependency into a full outage.

## Security in System Design: Boundaries and Safe Defaults [Axer Credit, Pluxee, AppFire]

This file avoids repeating the basic cloud or tenant-security content already covered in the earlier notes. The focus here is architecture-level service security and trust boundaries.

### Trust boundaries

Every service boundary is a trust boundary.

That means:

- input from external clients must be validated
- internal service calls must carry identity and authorization context
- downstream dependencies must not be trusted by default
- security controls should be enforced at edges and critical transitions

### Secure defaults

Good system design uses restrictive defaults:

- least privilege for service access
- explicit allowlists instead of implicit trust
- network isolation where needed
- default-deny policies for production access
- short-lived secrets and strong rotation practices

### Dependency security

A system is only as secure as its dependencies.

This includes:

- third-party packages and libraries
- base images and runtime dependencies
- infrastructure modules and managed services
- outdated clients or open-source libraries with known vulnerabilities

A mature engineering team continuously checks dependency hygiene and has a clear patching path.

## Cloud Configuration Management and Cost Optimization [Axer Credit, Pluxee, AppFire]

Cloud cost optimization is not just “turn down a few resources.” It is an architecture and usage problem.

### Configuration management

Good cloud systems keep config:

- environment-specific
- versioned
- auditable
- reviewed before rollout

Typical patterns:

- centralized config or secret stores
- environment-based values
- explicit defaults and safe parameters
- change approvals for production settings

### Cost optimization

Cost optimization should be tied to actual workload behavior.

Common issues:

- overprovisioned compute
- idle background jobs
- cross-region data transfer fees
- expensive logs and telemetry retained too long
- unnecessary duplication in storage and data pipelines

An architecture answer should mention that cost is a design outcome, not just a later accounting concern.

### The trade-off

Cheaper systems can be less resilient. More resilient systems can be more expensive. The job is to choose the right balance for the product’s criticality and traffic profile.

## Deployment Safety, Rollback, and Ownership [Axer Credit, Pluxee, AppFire]

Production safety is part of architecture, not an afterthought.

### Deployment safety

A stable deployment strategy includes:

- small, incremental changes
- automated validation before rollout
- canary or staged rollouts
- rollback readiness
- monitoring during and after deployment

### Rollback strategy

A rollback plan should not rely on memory. It should be explicit.

Examples:

- keep previous build artifacts available
- route traffic gradually
- keep database migrations reversible where possible
- have a rollback trigger based on metrics and error rates

### Operational ownership

If no one owns the service in production, the system is likely to decay.

Clear ownership means:

- a team is responsible for health and reliability
- there is a clear incident path
- service dependencies and owners are documented
- production readiness is part of engineering culture

## Service Boundaries and System Performance at Scale [Axer Credit, Pluxee, AppFire]

The real reason to split services is not “we want microservices.” The real reason is to reduce operational coupling and isolate performance problems.

A system that is too coupled will experience:

- cascading latency
- slow queue growth
- high DB contention
- noisy-neighbor degradation
- complicated incident response

Good boundary design keeps failures local and makes it possible to scale a hot path without paying the full cost for the whole system.

## Common Interview Framing [Axer Credit, Pluxee, AppFire]

A senior answer usually looks like this:

1. Identify the core business capabilities.
2. Define ownership and data sources.
3. Choose the minimum viable decomposition.
4. Set explicit contracts and compatibility rules.
5. Add caching only where invalidation is clear.
6. Measure bottlenecks before optimizing.
7. Add rate limiting and resiliency to protect critical paths.
8. Define deployment safety and rollback.

This is the difference between “I can draw boxes” and “I can design systems that stay reliable under load.”

## Typical Interview Questions [Axer Credit, Pluxee, AppFire]

### Question 1

When should you choose a modular monolith instead of microservices?

Expected answer:

When the domain is still changing, the team is small, the operational burden of distributed systems is not yet justified, and the main challenge is shipping product value quickly. A modular monolith reduces complexity while preserving clear boundaries.

### Question 2

How do you decide where to split a service boundary?

Expected answer:

By business capability and ownership, not technical convenience. The service should own a domain concept, maintain a clear source of truth, and expose stable contracts. If a boundary causes too much coordination or too many network calls, it is probably too fine-grained.

### Question 3

How do you handle backward compatibility in an API contract?

Expected answer:

Use additive changes, versioning when necessary, explicit deprecation windows, and consumer-driven contract tests. Breaking changes should be treated as a migration event, not a routine update.

### Question 4

Why is caching harder than it looks?

Expected answer:

Because the hard part is invalidation, stale data, and correctness under concurrency. A cache can improve latency but also create silent inconsistencies if the cache lifecycle is not designed carefully.

### Question 5

What is the difference between a slow system and a system that is failing under load?

Expected answer:

A slow system has latency issues. A failing-under-load system has saturation, queue growth, timeouts, retries, or dependency collapse. The right fix may be rate limiting, queueing, circuit breaking, or isolating and scaling the hot path.

### Question 6

What makes a service boundary “good” in production?

Expected answer:

It has clear ownership, stable contracts, limited cross-service chatter, manageable failure modes, and well-defined data ownership. A good boundary reduces operational surprises.

### Question 7

What is the biggest risk in a zero-downtime deployment?

Expected answer:

The biggest risk is hidden compatibility issues or failed rollouts that are not observable fast enough. A strong deployment plan includes staged rollout, rollback triggers, and explicit monitoring before and after deployment.

## Final Summary [Axer Credit, Pluxee, AppFire]

This file is about architecture discipline rather than hype.

The strongest system design answers emphasize:

- clear ownership and data boundaries
- explicit contracts and compatibility management
- performance debugging before premature optimization
- caching as a correctness trade-off
- rate limiting and degraded behavior under pressure
- deployment safety and operational ownership

A well-designed system is not the one with the most services. It is the one whose boundaries and performance controls are understandable, observable, and recoverable under real failure.
