# Testing Strategy, Performance, and Operations

Scope: how to validate system behavior, detect performance regressions, and operate production services safely without treating testing and monitoring as afterthoughts.

## How To Use This File In Interviews

Use this file when the interviewer asks:

- "How do you test a backend system before production?"
- "What is the difference between unit, integration, and contract tests?"
- "How do you know if a service is ready for production?"
- "What metrics do you watch when a system is under load?"
- "What does incident response look like in a real production outage?"

This file intentionally avoids repeating earlier architecture topics. It focuses on evidence-based validation and operational execution: what to test, what to measure, and how to respond when production fails.

## Why Testing Strategy Matters [Axer Credit, Pluxee, AppFire]

A system is not considered reliable because it “works locally.” It is reliable because the team can detect failures before they reach users and respond quickly when they do.

A strong testing strategy answers four questions:

- Does the code satisfy business rules?
- Does it work when dependencies are real and slow?
- Does it remain compatible with other systems?
- Can we detect and recover from failures quickly in production?

This is why the best organizations combine layered testing with operational monitoring.

## Unit Testing: Business Logic and Invariants [Axer Credit, Pluxee, AppFire]

Unit tests are about checking the smallest meaningful behavior in isolation.

They are best used for:

- business rules
- edge cases and boundary conditions
- validation logic
- deterministic transformations and calculations
- invariants such as “a refund cannot exceed the original payment”

### Good unit tests

A good unit test checks the actual logic of a function or class without depending on databases, network calls, or infrastructure.

Examples:

- tax calculation for different inputs
- status transition validation
- idempotency logic for duplicate requests
- inventory reservation invariants

### Example of a strong invariant

```ts
it("rejects a refund greater than the original payment", () => {
  const result = applyRefund({
    originalAmountCents: 5000,
    refundAmountCents: 6000,
  });
  expect(result.ok).toBe(false);
});
```

This is valuable because it protects a core business rule with a deterministic test.

### What unit tests do not cover well

They do not prove:

- that the database transaction works correctly
- that a queue consumer handles retries properly
- that an external provider failure is handled safely
- that two services work together under real conditions

That is why unit tests are necessary but not sufficient.

## Integration Testing: Real Dependencies and Failure Modes [Axer Credit, Pluxee, AppFire]

Integration tests validate behavior with real components that are close to the production environment.

This usually includes:

- real database transactions
- broker interactions like Kafka or RabbitMQ
- Redis and cache behavior
- HTTP clients to staging or mock external services
- config and secret loading

### Why integration tests matter

Many production bugs appear only when code interacts with:

- DB constraints and transaction boundaries
- retries and occasional timeouts
- queue redelivery
- provider outages or partial failures

A service can pass unit tests and still fail in production because the real system has a different contract than the mock assumptions.

### Good integration testing examples

- create a transaction that fails midway and verify rollback semantics
- push a message to a queue and verify the consumer processes it exactly once at the business level
- simulate a payment provider timeout and verify the application records the right retry behavior
- confirm that stale or inconsistent cache state does not put the system into an invalid state

### A strong interview answer

A strong answer is:

- unit tests protect logic
- integration tests protect wiring and environments
- both are needed

Without integration tests, you are testing idealized conditions instead of the actual distributed environment.

## Contract Testing: Compatibility Between Services [Axer Credit, Pluxee, AppFire]

Contract testing checks that service producers and consumers agree on the input/output shape and behavioral promises.

This is especially valuable in APIs and event-driven systems.

### Why it matters

When a producer changes a payload or behavior, consumer services can break even if the producer still “works.”

Examples:

- a field is renamed without warning
- a status code changes meaning
- an event schema becomes incompatible with downstream consumers
- a response object drops required fields

### Common contract testing patterns

- provider verifies response schema and semantics
- consumer defines expected contract
- CI fails when the contract is broken
- event schemas are versioned and validated

This is often a better safety net than “hope the other service handles it.”

## Load Testing: Throughput, Latency, Saturation, and Bottlenecks [Axer Credit, Pluxee, AppFire]

Load testing answers the question: what happens when the system is under realistic demand?

### Key metrics

A good load test tracks:

- throughput: requests per second or events per second
- latency percentiles: p50, p95, p99
- error rate
- saturation points
- queue growth and backlog
- database or dependency pressure

### Important distinction

“Works under one request” is not the same as “works under sustained load.”

A system may look stable until:

- CPU usage hits a limit
- connections to the database saturate
- upstream provider retries create a queue storm
- a cache gets hot and starts failing

### Common bottleneck types

- DB CPU or lock contention
- connection pool exhaustion
- network latency or dependency slowness
- queue buildup after a downstream outage
- memory pressure and GC pauses
- app-level CPU hotspots due to serialization or parsing

A mature load test does not just measure “peak request count.” It identifies the limiting resource and the failure mode.

## Observability: Logs, Metrics, Traces, and Alerts [Axer Credit, Pluxee, AppFire]

Observability is the ability to answer: what is failing, where, and why?

### Structured logs

Structured logs should contain:

- request id or trace id
- service name
- tenant or user id when relevant and safe
- action or event name
- status code or result
- duration and error metadata

Without structured logs, a production investigation becomes guesswork.

### Metrics

Metrics help identify trends and thresholds.

Examples:

- HTTP latency by endpoint
- error rate by service
- queue depth
- DB connection count
- CPU and memory saturation
- retry counts and timeout counts

These are the numbers that let teams react before a user-visible outage becomes severe.

### Traces

Distributed tracing helps connect a single request or workflow across services.

This is critical when:

- a request travels through multiple services
- events cross queue boundaries
- a failure appears in one component but originates upstream

A trace usually includes a correlation ID and spans for each subsystem.

### Alerts

Alerts should be based on user impact and service health, not just raw infrastructure noise.

Examples of good alerts:

- p95 latency above threshold for a critical endpoint
- queue backlog rising faster than expected
- error rate increasing for checkout requests
- dead-letter queue count above a threshold

Bad alerts are noisy, non-actionable, or unrelated to business impact.

## Incident Response: Reproduce, Mitigate, Determine Root Cause [Axer Credit, Pluxee, AppFire]

Production incidents are not just about fixing the immediate symptom. They are about creating a repeatable system for learning and prevention.

### Typical incident flow

1. Detect and triage the incident.
2. Establish the blast radius and user impact.
3. Mitigate the immediate issue.
4. Preserve evidence and logs.
5. Identify root cause.
6. Apply a fix and verify recovery.
7. Write postmortem follow-ups.

### Reproduction

A strong incident process often begins by asking:

- what changed?
- what spike or spike pattern preceded the issue?
- which workers/providers were affected?
- what dependencies failed?

Without a reproduction path, teams often guess at the cause.

### Mitigation before perfect root cause

Sometimes the fastest path is to:

- turn off a failing feature flag
- reduce concurrency
- drop or throttle a noisy worker
- isolate a failing dependency
- reroute traffic to a healthier region

This is part of good operational maturity.

### Postmortem culture

A good postmortem asks:

- what failed?
- why did it fail?
- why did we not detect it earlier?
- what can we automate to prevent recurrence?

This is how engineering teams improve, not just react.

## Production Readiness: What “Ready” Means [Axer Credit, Pluxee, AppFire]

A service is typically production-ready when it has:

- deterministic tests for critical logic
- real integration coverage for key workflows
- contract checks for shared interfaces
- observability for core user journeys
- alerting tied to actual service health
- backup rollback strategy and deployment controls
- explicit ownership and runbooks

This is a better definition than “it works in staging once.”

## Security in Operations: Secrets, Authorization, and Dependencies [Axer Credit, Pluxee, AppFire]

Security is operationally important because production failures often involve credentials or unsafe dependency updates.

### Secrets handling

Do not store secrets in code or plain text config files.

Use:

- secret managers
- short-lived credentials
- environment injection
- rotation procedures

### Authorization checks in operations

Even internal services must enforce identity and permission checks.

For example:

- admin actions require higher privilege
- system-to-system access uses scoped identities
- service credentials are separated by purpose

### Dependency vulnerabilities

A production system is only as safe as the libraries and base images it runs.

Teams need:

- dependency scanning
- patching discipline
- reviewed upgrades
- awareness of security advisories

## Docker, Kubernetes, and CI/CD Fundamentals [Axer Credit, Pluxee, AppFire]

This is expected in many interview conversations, but the focus should remain practical.

### Docker

Docker packages application dependencies into a consistent runtime unit.

Used well, it improves repeatability across local, CI, and production.

Typical concerns:

- image size and attack surface
- caching strategy
- environment consistency
- base image hygiene

### Kubernetes

Kubernetes orchestrates containerized workloads.

Key concepts:

- pods and replicas
- readiness and liveness probes
- deployments and rolling updates
- services and load balancing
- autoscaling
- resource limits and requests

A strong answer explains when orchestration helps and when it adds complexity.

### CI/CD

CI/CD should automate validation and release safety.

Typical pipeline stages:

- lint and type checks
- unit tests
- integration tests
- security scanning
- deployment gates
- rollout with monitoring

A mature team treats releases as controlled workflows, not “push to prod and watch.”

## Testing and Operations as a System [Axer Credit, Pluxee, AppFire]

The most important point is that testing and operations are connected.

If you only test happy paths, you will miss production failure patterns.

If you only monitor after deploy, you are too late.

The strongest engineering teams combine:

- correct business logic tests
- realistic integration coverage
- contract validation with dependent services
- performance checking under realistic load
- measurable observability and alerting
- clear escalation and incident response procedures

## Common Interview Questions [Axer Credit, Pluxee, AppFire]

### Question 1

What is the difference between unit tests and integration tests?

Expected answer:

Unit tests verify isolated logic and invariants. Integration tests verify that the real system behaves correctly when connected to databases, message brokers, external services, and environment-specific configuration.

### Question 2

What should a production-ready service have beyond passing tests?

Expected answer:

It should have logs, metrics, traces, alerting, runbooks, rollback plans, and clear ownership. Good tests are necessary, but operational readiness matters just as much.

### Question 3

How do you test performance issues before they hit users?

Expected answer:

By running load and soak tests against realistic traffic shapes, measuring p95/p99 latency, queue growth, saturation, and bottlenecks, and validating that the system degrades gracefully rather than crashing.

### Question 4

What is the purpose of contract testing?

Expected answer:

To ensure service producers and consumers agree on payload and behavioral contracts, so changes do not silently break dependent systems.

### Question 5

How do you handle an incident in production?

Expected answer:

By triaging the blast radius, mitigating immediate risk, collecting evidence, identifying the root cause, applying a fix, verifying recovery, and writing a postmortem to prevent recurrence.

### Question 6

Why is observability so important?

Expected answer:

Because without logs, metrics, and traces, you cannot understand the actual failure path or know whether a mitigation worked. Observability turns guesswork into diagnosis.

### Question 7

Why is CI/CD important even if the code works locally?

Expected answer:

Because the real risk is not local correctness but release safety, environment consistency, and correctness under real deployment conditions. CI/CD helps standardize and verify those conditions.

## Final Summary [Axer Credit, Pluxee, AppFire]

This file is about proving that a system is healthy in both controlled and real environments.

The strongest engineering answers emphasize:

- layered validation: unit, integration, contract, and load testing
- metrics and traces that reveal the actual bottleneck
- operational readiness and graceful degradation
- response plans for incidents and outages
- secure operational practices and deployment safety

A service is not “done” when the feature works. It is done when the team can validate it, observe it, and recover from it under pressure.
