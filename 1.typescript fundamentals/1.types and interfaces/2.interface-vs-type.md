# Interface vs Type in TypeScript

## Core Idea

TypeScript offers two main tools for describing object shapes:

- `interface`
- `type` aliases

In common object-shape cases, they behave similarly.

## Basic Equivalence Example

```ts
type BirdType = {
  wings: 2;
};

interface BirdInterface {
  wings: 2;
}

const bird1: BirdType = { wings: 2 };
const bird2: BirdInterface = { wings: 2 };
```

Because TypeScript is structurally typed, compatible shapes can be assigned across both forms.

```ts
const bird3: BirdInterface = bird1;
```

## Extending and Composition

Both approaches support building on existing types.

- Type aliases use intersections (`&`)
- Interfaces use `extends`

```ts
type Owl = { nocturnal: true } & BirdType;
type Robin = { nocturnal: false } & BirdInterface;

interface Peacock extends BirdType {
  colourful: true;
  flies: false;
}

interface Chicken extends BirdInterface {
  colourful: false;
  flies: false;
}

let owl: Owl = { wings: 2, nocturnal: true };
let chicken: Chicken = { wings: 2, colourful: false, flies: false };
```

## Error Message Quality (Practical Preference)

A common recommendation is to prefer `interface` for object shapes because TypeScript error messages are often clearer and more focused.

```ts
owl = chicken;
chicken = owl;
```

## Open vs Closed Types

A key difference:

- Interfaces are open (can be merged)
- Type aliases are closed (cannot be re-declared)

### Interface declaration merging

```ts
interface Kitten {
  purrs: boolean;
}

interface Kitten {
  colour: string;
}
```

### Type alias re-declaration (not allowed)

```ts
type Puppy = {
  color: string;
};

type Puppy = {
  toys: number;
};
```

## Design Guidance

- For publicly exposed object contracts, `interface` is often the safer default.
- For advanced compositions (especially unions/tuples), `type` is often necessary.
