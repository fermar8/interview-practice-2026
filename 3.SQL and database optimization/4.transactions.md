# Database Transactions and Concurrency

## ACID Properties

Transactions rely on ACID guarantees:

1. Atomicity: all operations succeed or all roll back.
2. Consistency: each transaction moves DB from one valid state to another.
3. Isolation: concurrent transactions do not interfere incorrectly.
4. Durability: committed changes persist through failures.

## Commit vs Rollback

- `COMMIT`: permanently save transaction changes.
- `ROLLBACK`: undo all changes in the transaction and restore prior state.

## Race Conditions

Race conditions happen when concurrent transactions read/write overlapping data in unsafe order.

Potential impact:

- Lost updates
- Inconsistent results

Databases mitigate this via isolation controls such as locking or MVCC.

## Locking Basics

Locks coordinate concurrent access to data.

Common lock types:

- Shared lock: read access
- Exclusive lock: write access

## Pessimistic vs Optimistic Locking

### Pessimistic locking

- Locks early before changes
- Good under high contention
- Can increase blocking/deadlock risk

### Optimistic locking

- Avoids early locking
- Detects conflicts at commit time
- Works well when conflicts are rare
- Requires retry/conflict handling logic

## N+1 Query Problem

N+1 occurs when code runs:

- 1 query to fetch a list of items
- N additional queries (one per item) for related data

This can severely hurt performance. Prefer batching, joins, eager loading, or prefetch strategies.
