# Payment Correctness: Idempotency, Ledgers, and Reconciliation

Scope: Payment-specific correctness patterns for retries, money movement, state transitions, and external reconciliation.

## How To Use This File In Interviews

Use this file to answer one core question clearly:

- How do you prevent money from being duplicated, lost, or misreported when payments cross user requests, queues, retries, and external providers?

Interview goal:

- show that you understand payment correctness is not just a database problem
- explain how idempotency, ledger integrity, state machines, and reconciliation work together
- demonstrate practical patterns for unknown provider outcomes and duplicate events

High-signal answer pattern:

1. Define the business invariant.
2. Identify the system boundary and failure mode.
3. Explain the state transition and idempotency strategy.
4. Show how the ledger captures truth and how reconciliation closes gaps.
5. Mention retry semantics and how you handle unknown outcomes safely.

## Why Payment Systems Are Different [Axer Credit, Pluxee]

Payments are different from ordinary application writes because the business rule is strict:

- the customer must not be charged twice
- a merchant must not receive duplicate settlement
- the ledger must remain balanced
- the system must tolerate retries, delayed webhooks, and provider timeouts

This means payment correctness is usually driven by three ideas:

- idempotent operations
- immutable accounting records
- explicit reconciliation between internal state and external provider state

## Idempotency: The Core Safety Pattern [Axer Credit, Pluxee]

An idempotent payment operation is one that can be safely retried without creating a second charge or second fulfillment.

The most common pattern is a request idempotency key or payment intent ID.

### Example: client request idempotency

```http
POST /payments
Idempotency-Key: 8a4d2f6d-df9a-4f2a-b87d-9d4d4a7f0e2a
```

Server behavior:

- store the idempotency key with the payment intent
- if the same key is seen again, return the original result instead of creating a second charge
- keep the key long enough for retries but short enough to prevent indefinite key reuse

### Database pattern

```sql
CREATE TABLE payment_requests (
  id UUID PRIMARY KEY,
  idempotency_key TEXT NOT NULL UNIQUE,
  payment_intent_id UUID NOT NULL,
  status TEXT NOT NULL,
  amount_cents BIGINT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Then the write path is effectively:

```sql
INSERT INTO payment_requests (id, idempotency_key, payment_intent_id, status, amount_cents)
VALUES ($1, $2, $3, 'pending', $4)
ON CONFLICT (idempotency_key) DO NOTHING;
```

If the insert is rejected due to a duplicate key, the service should return the existing payment result rather than creating another charge.

### Why this matters

In payment systems, duplicate delivery is normal:

- client retry after timeout
- provider retry after network failure
- message redelivery from queue
- webhook replay from upstream systems

Without idempotency, a single user action can become multiple charges.

### If the request succeeds but the client times out

This is one of the most important interview questions in payments.

The correct reasoning is:

- the payment may have been recorded successfully
- the client may not have received the response
- the system must treat the original payment as authoritative, not create a second one

This is why the payment record should be keyed by a stable request identity, not by a best-effort client side guess.

### Idempotency retention and key reuse

A payment idempotency key should usually remain valid for a bounded period, such as:

- 24 hours for most customer-initiated payments
- longer for reconciliation and dispute workflows if needed

Never reuse the same key for a different business action. That is a common source of subtle charge duplication.

## Payment State Machines [Axer Credit, Pluxee]

A payment is not just a single boolean status. It usually moves through states.

Typical lifecycle:

- `created`
- `pending`
- `authorized`
- `captured`
- `settled`
- `failed`
- `reversed`
- `refunded`

### Why this matters

The state machine tells you what transitions are legal and what invariants must hold.

Examples:

- a payment cannot be captured twice
- a failed payment cannot later become settled
- a reversed payment should not remain in a positive balance state
- a refund should reference the original payment and a valid reason code

### Example design

```sql
CREATE TABLE payments (
  id UUID PRIMARY KEY,
  payment_intent_id UUID NOT NULL UNIQUE,
  amount_cents BIGINT NOT NULL,
  status TEXT NOT NULL CHECK (status IN (
    'created', 'pending', 'authorized', 'captured', 'settled', 'failed', 'reversed', 'refunded'
  )),
  provider_reference TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

The application should not mutate the payment state with ad-hoc SQL. It should transition through approved state logic.

## Payment-Specific Concurrency and Double-Spend Prevention [Axer Credit, Pluxee]

This file intentionally avoids repeating the general row-lock and Redlock theory already covered in the database and Redis notes. The payment-specific question is: how do we prevent duplicates and inconsistent balances in a money flow?

### The real failure mode

Two concurrent requests for the same payment intent may both reach the payment gateway or ledger service.

Without safeguards, you get:

- double charge
- duplicate authorization
- incorrect settlement amount
- inconsistent balance state

### Payment-specific safeguards

Use a combination of:

- unique keys on payment intent or provider reference
- conditional updates on status transitions
- single-writer ownership for a payment record
- explicit retry checks for unknown provider outcomes

Example:

```sql
UPDATE payments
SET status = 'captured', updated_at = NOW()
WHERE id = $1
  AND status IN ('authorized', 'pending');
```

If the update affects zero rows, the system knows the state transition was not valid and should not continue as if it succeeded.

### Important idea

In payment systems, the correctness boundary is usually the payment intent or external reference, not just the raw database row.

You must design for:

- retry after timeout
- duplicate webhook delivery
- partial provider success
- eventual reconciliation

## Ledger Design: Double-Entry and Immutable Records [Axer Credit, Pluxee]

A payment ledger is not just a balance column. It is usually an append-only journal of movements.

### Double-entry principle

Every value-moving action should have a balanced effect.

Example:

- customer balance decreases by 1000 cents
- merchant balance increases by 1000 cents
- processing fee or reserve entry may also exist

A simple ledger table could look like:

```sql
CREATE TABLE ledger_entries (
  id UUID PRIMARY KEY,
  payment_id UUID NOT NULL,
  account_id UUID NOT NULL,
  direction TEXT NOT NULL CHECK (direction IN ('debit', 'credit')),
  amount_cents BIGINT NOT NULL,
  balance_after_cents BIGINT NOT NULL,
  entry_type TEXT NOT NULL,
  reference_id TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

This has a few benefits:

- each entry is immutable
- the business can audit and reconcile every movement
- the final balance becomes a derived value, not a mutable field that can be silently overwritten

### Available vs booked balance

This is a very common interview point in payments.

- available balance: funds that can be used immediately
- booked balance: funds recognized as committed in the ledger
- pending or reserved funds: not yet final

This distinction matters because a payment can be:

- authorized but not settled yet
- captured but awaiting clearing
- failed after partial action
- reversed due to dispute or refund

In product terms, a customer may see a pending deduction even though the final ledger entry is not fully settled yet.

## Reconciliation: Provider vs Internal State [Axer Credit, Pluxee]

Payment systems rarely have all truth in one place.

The internal system may think a charge succeeded, while the provider says it is pending, or vice versa.

That is why reconciliation matters.

### Typical reconciliation flow

1. Internal service records a payment intent.
2. Provider processes the charge and returns a result.
3. Webhook or polling later confirms the final state.
4. A reconciliation job compares provider data with internal data.
5. Any mismatch is classified as pending, duplicate, or failure.

### Reconciliation questions to ask

- Did we receive a successful provider response but not store the internal state?
- Did we charge the customer but never capture the final provider event?
- Did we receive a duplicate webhook for the same event ID?
- Is the provider amount different from the internal transaction amount?

### Payment-specific reconciliation example

```text
Internal record: payment_id=123, status='pending'
Provider record: payment_id=123, status='captured', amount=5000
Result: mark payment as captured and reconcile mismatch queue item
```

If provider outcome is unknown:

- do not assume failure
- do not assume success
- place the payment in a `pending_unknown` or `needs_reconciliation` state
- retry status check or webhook handling later

This is much safer than guessing based on a timeout.

## Event-Driven Reliability in Payment Systems [Axer Credit, Pluxee]

Payment flows are usually not purely synchronous. Webhooks, async jobs, and retries are normal.

### At-least-once delivery means duplicates are expected

A provider may retry a webhook or a queue may redeliver a message.

So the system must be designed around:

- unique event IDs
- idempotent handlers
- rule-driven state transitions
- deduplication on the event key

Example:

```sql
INSERT INTO webhook_events (event_id, provider, payload, status)
VALUES ($1, $2, $3, 'received')
ON CONFLICT (event_id) DO NOTHING;
```

If the same webhook comes in again, the system treats it as a duplicate and does not create a new ledger entry or payment mutation.

### Why "exactly once" is usually a lie

In payment systems, exactly-once semantics are usually approximated via:

- idempotency keys
- deduplication tables
- database uniqueness constraints
- carefully ordered state transitions

The goal is not magical exactly-once processing. The goal is to make retries safe and auditable.

## Unknown Outcome Handling [Axer Credit, Pluxee]

This is one of the classic payment-design problems.

### Scenario

The app sends the charge request to the provider, but due to timeout or network issue the app does not know whether the provider processed it.

Bad options:

- retry blindly and charge twice
- assume failure and leave the customer unpaid
- mark the payment as done without verifying the provider state

Better approach:

- store the payment request with a unique identifier
- query the provider for status using that identifier
- if still unresolved, mark the payment as `pending_unknown`
- reconcile later with provider reports or webhooks

This is often more correct than making a guessed decision under uncertainty.

## Reversal, Refund, and Correction Patterns [Axer Credit, Pluxee]

Payment systems must support reversals and adjustments cleanly.

Typical patterns:

- refund: reverse a captured payment
- chargeback: customer dispute after settlement
- reversal: cancel a pending or authorized payment
- adjustment: correct an accounting mismatch by a ledger entry

The key design rule is:

- do not mutate the original ledger entry in place if the system wants auditability
- instead, append a reversal or correction entry that makes the final state correct

Example:

```sql
INSERT INTO ledger_entries (
  id, payment_id, account_id, direction, amount_cents, balance_after_cents, entry_type
)
VALUES (
  'rev-1', 'p-42', 'merchant-account', 'credit', 5000, 250000, 'refund'
);
```

This keeps the original payment trace intact while recording the correction.

## Payment-Specific Interview Answers [Axer Credit, Pluxee]

### 1) "How do you prevent double charging?"

Strong answer:

- generate a stable request ID / payment intent ID
- store it in a deduplication table
- enforce uniqueness at the database level
- return the original outcome for retries

### 2) "What do you do when a provider times out after the charge may have succeeded?"

Strong answer:

- do not guess
- store the payment request and query provider status with the same reference
- mark the state as `pending_unknown` and reconcile asynchronously
- only finalize when the provider state is known

### 3) "Why are ledger entries important in payments?"

Strong answer:

- they maintain an audit trail
- they make corrections explicit and reviewable
- they reduce silent data corruption and allow reconciliation

### 4) "What is the difference between a payment status and a ledger entry?"

Strong answer:

- the status tells the workflow state
- the ledger records actual money movement and balances
- they are related but not the same concept

### 5) "Why do duplicate webhooks matter so much?"

Strong answer:

- upstream systems retry messages aggressively
- a webhook is not proof of unique processing unless the application deduplicates it
- deduplication is a core part of payment correctness

## Common Mistakes To Avoid

- using a single mutable `balance` column without immutable ledger history
- retrying payment creation without a stable idempotency key
- assuming that a timeout means failure
- treating webhooks as unique without deduplication checks
- confusing business state with accounting state
- splitting reconciliation logic across multiple code paths instead of centralizing it

## 60-Second Interview Summary

"Payment correctness is not about making a single request atomic in every system; it is about making money movement safe under retries, duplicates, provider uncertainty, and partial failure. I design around idempotency keys, unique database constraints, explicit payment state transitions, immutable ledger entries, and a strong reconciliation layer that can classify unknown outcomes. In payment systems, correctness comes from making duplicate execution and ambiguous outcomes safe, not from assuming the network or provider will behave perfectly."
