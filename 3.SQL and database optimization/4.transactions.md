# Database Transactions

## ACID Properties
ACID ensures database operations are reliable and maintain data integrity.

### Atomicity
Treats a transaction as a **single unit of work**:
- Either all operations complete successfully
- Or none of them complete
- If any operation fails, the entire transaction is rolled back

### Consistency
Brings the database from **one valid state to another valid state**:
- All data written must be valid according to defined rules
- Includes constraints, cascades, and triggers

### Isolation
**Concurrent transactions do not interfere** with each other:
- Each transaction is isolated from others
- Operations of one transaction don't affect others
- Achieved through locking or multi-version concurrency control (MVCC)

### Durability
**Once committed, always committed**, even on system failure:
- Ensures permanent storage
- Achieved through transaction logs and recovery mechanisms

## Commit and Rollback

### Commit
Saves all changes made during a transaction:
- All operations successfully completed
- Changes are now permanent in the database

### Rollback
Undoes all changes made during a transaction:
- If any operation fails
- If explicitly rolled back by user
- Database returned to state before transaction began
- Maintains data integrity

## Race Conditions
Occur when multiple transactions try to access and modify the same data concurrently.

### Example Problem
Two transactions updating the same record simultaneously:
- Can lead to inconsistent data
- One transaction can overwrite changes from another

### Prevention
- Use **locking mechanisms**
- Use **multi-version concurrency control (MVCC)**
- Ensures transactions are isolated and don't interfere

## Locking Mechanisms
Control access to data in a database:

### How It Works
When a transaction accesses data:
- Acquire a lock on that data
- Prevents other transactions from accessing/modifying it
- Lock is released after transaction completes

### Lock Types
- **Shared locks** – For reading
- **Exclusive locks** – For writing

### Locking Strategies
- **Pessimistic locking** – Acquire locks before operations
- **Optimistic locking** – Check for conflicts on commit

## Pessimistic Locking
Acquires locks **before** performing operations.

### Characteristics
- Assumes conflicts are likely to occur
- Locks data to prevent concurrent access
- Can lead to better performance with high contention

### Disadvantages
- Risk of deadlocks if not managed properly

## Optimistic Locking
Does **not** acquire locks; allows concurrent access.

### Process
1. Multiple transactions access same data concurrently
2. Check for conflicts when ready to commit
3. If conflict detected, rollback and retry

### Characteristics
- Assumes conflicts are rare
- Better performance with low contention
- Requires complex error handling

## N+1 Query Problem
Occurs when an application executes:
1. **One query** to retrieve a list (the "n" query)
2. **One query per item** to retrieve related data (the "+1" queries)

### Example Problem
```
// Get all users
Query 1: SELECT * FROM users;
// Get posts for each user
Query 2: SELECT * FROM posts WHERE userId = 1;
Query 3: SELECT * FROM posts WHERE userId = 2;
Query 4: SELECT * FROM posts WHERE userId = 3;
// ... and so on for each user
```

### Impact
- Large number of queries executed
- Significantly degrades performance
- Database load increases substantially

### Solution
Use JOIN or eager loading to fetch related data in one query
