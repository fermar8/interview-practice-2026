# Redis Caching and Distributed Coordination

Scope: Cache strategies, TTL and eviction behavior, atomic operations, and distributed locking trade-offs.

- When should I use Redis for caching, and when is Redis the wrong tool for coordination or correctness-critical state?

Interview goal:

- Show that you understand the difference between a cache and a coordination primitive.
- Explain why Redis is fast, but also why cache correctness is a system design problem.
- Demonstrate practical trade-offs: hit rate, invalidation, TTL, locking, and failure recovery.

## Why Redis Is So Useful [Pluxee]

Redis is a high-performance, in-memory data store that can be used for caching, message brokering, and distributed coordination.

Redis is attractive because it is:

- in-memory and extremely fast
- simple for common data structures like strings, hashes, sets, sorted sets
- good for temporary data, hot keys, and coordination primitives
- useful for rate limiting, sessions, leader election hints, and caching

But Redis is not a silver bullet. It is often used to reduce load or improve read latency, but it does not magically solve the correctness challenges of a distributed system.

### Strong interview framing

- "Redis is great at speed and operational simplicity, but correctness still depends on how we invalidate, refresh, and lock data."

## Cache vs Locking: The Two Main Use Cases [Pluxee, AppFire]

Redis is often used in two different ways:

1. As a cache for hot or frequently repeated reads.
2. As a coordination tool for distributed locking, rate limiting, or leader election hints.

These are not the same problem.

A cache is usually allowed to be stale for a while.
A lock is a correctness mechanism: it must be safe under partial failure and network issues.

This distinction matters a lot in interviews.

## Caching Strategies [Pluxee, AppFire]

### Cache-Aside (Lazy Loading)

This is the most common pattern.

Flow:

1. Application checks Redis.
2. If cache miss, query the database.
3. Write the result to Redis.
4. Return data to caller.

Example:

```ts
const user = await redis.get(`user:${userId}`);
if (user) return JSON.parse(user);

const dbUser = await db.users.findById(userId);
await redis.set(`user:${userId}`, JSON.stringify(dbUser), { EX: 300 });
return dbUser;
```

Why it is popular:

- simple to reason about
- only caches what is actually read
- avoids caching cold data unnecessarily

Trade-offs:

- cache stampede risk on thundering herd misses
- stale data until refresh
- requires invalidation logic on writes

### Write-Through

The application writes to the database and the cache is updated in the same write path.

Good for:

- low-latency, read-heavy systems
- systems where cache freshness matters

Typical flow:

```text
write to DB -> write to Redis -> return success
```

Advantages:

- strong cache freshness after writes
- fewer surprises for readers

Disadvantages:

- write path becomes more complex
- duplicate writes must be coordinated carefully
- if cache write fails, you may end up with DB and cache divergence. This can be mitigated with careful error handling and retry logic.

### Write-Behind (Async Write Back)

The app writes to Redis first or queues the write to process later, and the database is updated asynchronously.

This is often used in systems that care about latency more than strict consistency.

Example:

```text
update Redis quickly -> enqueue background DB write -> later flush to DB
```

Pros:

- very fast user-facing writes
- good for bursty traffic

Cons:

- risk of data loss if Redis or the queue fails before flush
- harder to reason about replay and consistency
- not ideal for critical financial or inventory updates without careful design

### Read-Through

A read-through cache sits in front of the data source, and the cache loads missing data automatically.

This is often implemented by the application framework or a caching layer rather than manual code.

Difference from cache-aside:

- cache-aside is explicit in app code
- read-through often hides the fetch logic behind the cache abstraction

### Which strategy should you choose?

Interview answer pattern:

- "I almost always start with cache-aside for straightforward app-level caching because it is explicit and easy to debug. For a write-heavy or correctness-sensitive system, I prefer write-through or a stronger data ownership model over write-behind."

## TTLs and Expiration [Pluxee, AppFire]

TTL matters because cache data eventually becomes stale.

### Absolute Expiration

A key expires after a fixed time, regardless of use.

```bash
SET user:42 '{...}' EX 300
```

Good when:

- data freshness matters
- stale data should be dropped after a bounded time

### Sliding Expiration

A key gets renewed whenever it is accessed.

This is useful for frequent hot objects that should stay cached while they are still being used.

### Why TTL matters in practice

Without TTL:

- stale data can persist forever
- invalidations become messy
- memory fills up

With TTL:

- you bound staleness
- you avoid unbounded memory growth
- you recover automatically from silent cache drift

### Stale-While-Revalidate

This is a common pattern for high-read systems.

- serve stale cache immediately
- trigger a background refresh
- let the system self-heal without making every request wait on a slow origin

Example:

```text
Cache hit within TTL -> return stale value quickly
Background refresh -> update cache asynchronously
```

This improves latency but introduces freshness trade-offs and should be used only when stale data is acceptable for a bounded period.

## Eviction Policies [Pluxee]

Redis must evict keys under memory pressure. The policy matters for behavior and operational tuning.

### LRU: Least Recently Used

Evicts the least recently accessed keys.

Good for:

- general caching workloads
- objects with naturally uneven access patterns

Bad for:

- workloads where popularity is not correlated with recency

### LFU: Least Frequently Used

Evicts keys with the lowest access frequency.

Good for:

- workloads with stable object popularity
- avoiding churn from repeatedly touching a few hot keys

Trade-off:

- more complex behavior and less intuitive debugging than LRU

### TTL-Based Expiration

Redis also evicts keys that are expired or near expiration.

Important distinction:

- an expired key is not necessarily removed immediately; it is lazily expired or cleaned in background sweeps
- memory pressure can trigger eviction of non-expired keys depending on configuration

### Interview discussion

- "LRU is good for caches with recency-based access patterns. LFU helps when some keys are consistently hotter than others. TTLs keep data bounded and predictable. You still need the right invalidation strategy, not just the right eviction policy."

## Atomic Operations: Why Redis Is So Good For Coordination [Pluxee]

Redis operations are atomic at the single-command level.

This is what makes it useful for counters, locks, and rate limiting.

### Example: Incrementing a counter

```bash
INCR api:requests:per-minute
```

This is atomic because no two clients can race and produce a lost increment.

### Example: Set-if-absent

```bash
SET lock:order:42 "holder" NX PX 5000
```

`NX` means only set if the key does not already exist.
`PX` means set a TTL in milliseconds.

This is common for simple distributed locks.

### Example: Lua scripts

Lua scripts are useful when you need multiple steps to be atomic as a single logical operation.

```lua
local current = redis.call('GET', KEYS[1])
if current then
  return current
end
redis.call('SET', KEYS[1], ARGV[1], 'EX', 60)
return ARGV[1]
```

Why this matters:

- avoid race conditions between read and write
- simplify lock or conditional update logic
- uphold atomicity for multi-step operations inside Redis

### Failure scenarios with atomic operations

Even with atomic commands, Redis does not solve all problems.

Examples:

- if the app crashes after setting a key but before cleanup, the lock may remain stale
- if two clients both set the same lock key with the same TTL, one may still win accidentally
- if a network partition occurs, clients may think they own a lock when they do not

That is why lock pattern design is subtle.

## Distributed Locks [Pluxee, AppFire]

### Simple lock pattern

```bash
SET mylock "client-1" NX PX 5000
```

This is a common first attempt, but it has important flaws.

Problems:

- if the process holding the lock crashes, the lock may remain forever until TTL expires
- TTL may expire while the operation is still running, causing another client to acquire the lock
- clock drift and network timeouts make lock correctness harder than it looks

### Redlock Algorithm

Redlock is a distributed lock algorithm that uses multiple Redis instances to reduce the chance of a single Redis failure causing a false lock acquisition.

Conceptually:

1. Acquire a lock on N independent Redis instances.
2. Set a short TTL on each lock.
3. Require majority approval to consider the lock acquired.
4. Release the locks by verifying ownership.

Why people use it:

- it reduces single-node lock dependency
- it makes a lock less likely to be lost due to one Redis instance failing

Why it is controversial:

- correctness is weaker than a single DB transaction
- clock skew can break assumptions
- lock TTL and fencing tokens are still required in many real systems
- Redis is often not the right place for distributed locks if the correctness requirement is very strict

### Fencing tokens

A fencing token is a monotonically increasing number given to each lock owner.

It solves this problem:

- client A acquires lock
- client A is slow and its lock expires
- client B acquires the lock
- client A resumes and performs stale writes

Without fencing tokens, stale owners may still write after a lock has expired. With fencing tokens, the system rejects outdated writes by checking token version numbers.

This is particularly important in systems with leased locks and distributed workers.

### Best practices for distributed locks

- Use a short TTL with renewal if needed.
- Make the lock name specific to the business resource.
- Use UUIDs or unique client IDs to verify ownership.
- Never hold a distributed lock over a long-running external call.
- Treat the lock as a coordination primitive, not as a replacement for application-level correctness.
- Prefer a database transaction or row lock when the correctness requirement is strict and local to one data store.

## Rate Limiting and Redis [Axer Credit, Pluxee, AppFire]

Redis is widely used to implement rate limits.

Examples:

- limit requests per IP
- limit API calls per user
- protect expensive endpoints from abuse

Pattern:

```bash
INCR user:42:requests
EXPIRE user:42:requests 60
```

Then check whether the count exceeds the threshold.

This is fast and effective, but only if your ratio limit is appropriate for the business problem.

## Redis Failure Modes You Need to Know [Pluxee, AppFire]

### Network partition

A client may lose contact with Redis but still think it owns a lock or has a valid key.

This can lead to:

- duplicate processing
- stale writes
- inconsistent coordination

### Crash after acquiring lock

If the lock owner crashes without releasing the lock, the key may remain until TTL expiration.

If the operation is still running, this can create a time window where another worker mistakenly assumes the resource is free.

### Clock drift

Redlock assumes clocks are not wildly skewed, but distributed systems often have clock unpredictability.

This is one reason why many systems avoid over-trusting time-based distributed coordination.

### Memory pressure and eviction

Cache keys may be evicted under memory pressure, which is acceptable for cache data but dangerous if the key is acting as a lock or a system-of-record object.

This is why Redis should not be used as the only source of truth for critical business state when data durability matters.

## Practical Interview Scenarios [Pluxee, AppFire]

### Scenario 1: Hot user profile cache

Need:

- reduce DB load for frequently requested profiles
- keep profile reads fast

Pattern:

- cache aside
- TTL 5–60 minutes
- invalidate on profile update

Answer:

- simple, effective, low-risk
- must handle stale profile writes and invalidation correctness

### Scenario 2: Inventory reservation

Need:

- prevent overselling during high concurrency

Pattern:

- use database transactions and row locks, not a Redis lock alone
- maybe use Redis for coordination hints but keep the real invariant in the database

Why:

- the business invariant is too important to rely solely on a lock in an external cache

### Scenario 3: Rate limiting an API

Need:

- protect the service from abusive volume

Pattern:

- use Redis counters with TTL windows
- reject when threshold exceeded

This is a common, good use of Redis because the operation is naturally ephemeral and retryable.

## Deep Mock Questions Focused On This File

### 1) "Why is Redis often used as a cache, but not as the system of record?"

Strong answer:

- Redis is fast and convenient, but it is primarily an in-memory data store with bounded persistence semantics.
- Caches are allowed to be stale and evictable.
- System-of-record data should usually live in a durable relational or persistent storage layer.

### 2) "What is the difference between cache-aside and write-through?"

Strong answer:

- Cache-aside loads data on demand and invalidates when writes occur.
- Write-through updates the cache as part of the write path.
- Cache-aside is simpler and more common; write-through gives stronger freshness assumptions but more write complexity.

### 3) "Why are TTLs so important in a cache?"

Strong answer:

- TTLs bound staleness and memory use.
- They help recover from bad invalidation logic and temporary failures.
- Without TTLs, caches become stale and eventually unbounded.

### 4) "What is a cache stampede, and how do you prevent it?"

Strong answer:

- A cache stampede happens when many clients miss at the same time and all request the same slow origin simultaneously.
- Prevent by using per-key locking, single-flight patterns, stale-while-revalidate, or background refresh logic.

### 5) "Why is `SET key value NX PX ttl` not a perfect distributed lock?"

Strong answer:

- it can fail if the process crashes before unlocking
- TTL expiry can create a lock gap
- no fencing token means stale owners may still write after a lock has expired
- distributed coordination is hard, especially across network partitions

### 6) "When would you choose a database lock over a Redis lock?"

Strong answer:

- when the invariant is critical and local to one database
- when the operation is part of a strong transactional system
- when you need a single source of truth for correctness rather than a hint-based coordination mechanism

### 7) "What is a good reason to prefer a saga over a distributed 2PC?"

Strong answer:

- a saga makes recovery explicit and business-aware
- 2PC is difficult to operate, coordinate, and recover from
- many real systems have cross-service workflows that cannot be safely treated as one atomic unit

### 8) "Why is idempotency so important in distributed systems built on Redis or message queues?"

Strong answer:

- retries happen all the time
- duplicates are not exceptional; they are expected
- idempotent keys and deduplication patterns make the system safe under repeated delivery

## Common Mistakes To Avoid

- Using Redis as the only source of truth for critical state.
- Setting long lock TTLs and assuming the process will finish before expiry.
- Using cache invalidation patterns without a replay-safe update path.
- Ignoring cache stampede behavior under concurrent misses.
- Overusing write-behind caches when the business logic requires consistency.
- Treating distributed locks as if they guarantee correctness in every failure mode.

## 60-Second Interview Summary

"Redis is fast and useful, but its value depends on the pattern. I use it for caching hot reads, rate limiting, and low-latency coordination, but I do not treat it as a substitute for transactional correctness in critical business flows. Cache strategies need TTLs and invalidation logic, and distributed locks need careful TTL, ownership, and failure handling. The right answer is usually to keep the real invariant in durable storage and use Redis as an acceleration or coordination layer, not as the sole source of truth."
