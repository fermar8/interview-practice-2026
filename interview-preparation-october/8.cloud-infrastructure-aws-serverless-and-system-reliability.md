# Cloud Infrastructure: AWS, Serverless, and System Reliability

Scope: AWS service boundaries, serverless architectures, reliability engineering, deployment practices, and cloud security fundamentals for real-world system design interviews.

## How To Use This File In Interviews

Use this file when the interviewer asks questions such as:

- "How would you design a reliable API on AWS?"
- "Why choose Lambda over containers or EC2?"
- "How do you handle retries, duplicate events, and partial failures?"
- "What would you do if a downstream service is slow or unavailable?"
- "How do you secure a multi-tenant API in a cloud environment?"

The core message is simple:

- cloud systems are reliable when they are designed for failure, not when they assume services always work
- serverless does not remove operational complexity; it changes where that complexity shows up
- the best cloud architecture combines clear ownership boundaries, observability, least privilege, and graceful degradation

## Why Cloud Architecture Matters [Axer Credit, Pluxee, AppFire]

In a cloud system, the main challenge is not just deploying code. It is managing:

- regional and availability-zone failure
- network latency and timeouts
- external dependency outages
- burst traffic and cold starts
- security boundaries across services
- event duplication and ordering issues

A production cloud design usually aims for a combination of:

- fault isolation
- retry budgets
- idempotent business actions
- controlled concurrency
- observable failure signals

The SaaS and platform interviews almost always expect you to reason about failure modes, not just happy-path architecture.

## AWS Core Building Blocks: Service Boundaries [Axer Credit, Pluxee, AppFire]

A strong answer in interviews starts with understanding the purpose of each AWS primitive.

### API Gateway

API Gateway is usually the entry point for internet-facing HTTP or REST APIs.

It handles:

- request routing
- throttling and rate limiting
- authentication and authorization hooks
- request validation
- request/response transforms
- integration with Lambda, ALB, ECS, or other backend services

Important design question:

- Should API Gateway directly call Lambda or should it sit in front of an internal service layer?

Common pattern:

- API Gateway exposes public API surface
- business logic lives in Lambda or service containers
- downstream dependencies are isolated behind queues, caches, and databases
- authorization is enforced before business logic executes

### Lambda

Lambda is a serverless compute primitive designed for event-triggered or short-lived workloads.

Strengths:

- fast to deploy and scale
- works well for bursty workloads
- pay per invocation
- easy integration with S3, SQS, SNS, DynamoDB Streams, EventBridge, and API Gateway

Weaknesses:

- cold starts can cause latency spikes
- execution time and memory limits exist
- local state is ephemeral
- heavy workloads can be costly if not designed carefully

A strong interview answer often mentions:

- keep functions small and focused
- avoid doing large data processing in a single Lambda if the job can be streamed or batched
- use async patterns for non-user-facing work
- set explicit timeouts and keep them realistic

### SQS and event buffering

SQS is a durable queue used to decouple producers and consumers.

Why it matters:

- protects the producer from downstream slowness
- smooths traffic spikes
- enables retry isolation
- gives you a place to store work while a consumer is unhealthy

There are two important characteristics:

- at-least-once delivery
- no ordering guarantee for standard queues

That means the application must be built to handle repeated delivery and duplicate processing.

### SNS and fan-out

SNS is a pub/sub system used to broadcast events to multiple subscribers.

Typical pattern:

- payment created event published to SNS
- analytics service subscribes
- email service subscribes
- audit service subscribes

This is useful when many systems need to react to the same event without direct coupling.

### IAM

IAM is probably the most important security primitive in AWS.

Core idea:

- create least-privilege roles
- avoid long-lived access keys in application code
- give services only the permissions they need
- separate identity of the service from the identity of the user

A strong interview answer should distinguish:

- authentication: who are you?
- authorization: what are you allowed to do?

For example:

- a user signs in with a session token: authentication
- the backend checks that the user can read this account: authorization

In AWS, service-to-service access is usually done via IAM role assumption, not by hardcoded credentials.

### VPC, subnets, security groups

A VPC defines network isolation.

Key ideas:

- public subnets for internet-facing resources
- private subnets for internal services
- security groups as stateful virtual firewalls
- NACLs as subnet-level filtering

This matters because serverless services often appear to be “just functions,” but they still sit inside a network boundary and need secure connectivity patterns.

## Serverless Architecture: Cold Starts, Timeouts, and Concurrency [Axer Credit, Pluxee, AppFire]

Serverless is attractive, but the design tradeoff is real.

### Cold starts

A cold start happens when a Lambda function is initialized for the first time or after inactivity.

This introduces:

- higher latency on first invocation
- slower startup for large dependencies
- less predictable performance during bursts

Mitigations include:

- provisioned concurrency
- smaller deployment packages
- reducing initialization work from the cold path
- warm-up patterns only when justified

In interviews, do not say “Lambda always scales instantly.” That is not fully true. It can scale, but cold starts and concurrency throttling still matter.

### Concurrency and rate limits

AWS imposes concurrency controls.

This means your service can be rate-limited or throttled during bursts.

Common design responses:

- queue work instead of sending spikes directly to the worker
- use SQS with concurrency controls
- apply rate limiting and backpressure
- isolate workloads by purpose

### Timeouts

Every integration has a timeout budget.

For example:

- API Gateway timeout may be lower than downstream Lambda timeout
- Lambda has an execution limit
- database calls and HTTP dependencies must be treated as potentially slow

A good service design will:

- set conservative timeouts
- fail fast when slow dependency is detected
- avoid waiting forever in a request path
- move long-running tasks to async jobs

### Retries and failure handling

Serverless systems often rely on retries, but retries can create duplicate work unless designed with idempotency in mind.

This is one of the most important reliability patterns:

- retries should be bounded
- retries should be exponential backoff with jitter
- permanent failures should go to a dead-letter queue
- idempotent business actions should be enforced using unique keys

## Event-Driven Design: Real Semantics [Axer Credit, Pluxee, AppFire]

Event-driven systems are a core pattern in AWS, but they are often misunderstood.

### Synchronous vs event-driven

Synchronous request-response is best for:

- user-triggered operations that need immediate feedback
- workflows with strict latency needs
- operations where user waits for a result

Event-driven is best for:

- decoupling independent services
- handling bursts and spikes
- asynchronous workflows like notifications, analytics, and background processing

The main tradeoff:

- synchronous designs are simpler to reason about
- event-driven designs are more scalable and resilient but more complex because of eventual consistency

### Duplicate delivery

At-least-once delivery means a message may be processed more than once.

This is normal in distributed systems, and a system that does not assume duplicates is fragile.

Design responses:

- store a unique processing key
- enforce idempotency at the business layer
- use a database unique constraint or dedupe table
- treat duplicate events as harmless and expected

### Ordering

Some systems require ordering, but standard queues and pub/sub do not promise total ordering.

If order matters, you need some explicit mechanism:

- partitioned streams
- message keys
- ordered topics or queues
- single-writer semantics for a business entity

For example, if you have events for the same order id, route them to the same partition so they are processed in order.

### Dead-letter queues

A dead-letter queue (DLQ) captures messages that repeatedly fail.

This matters because without a DLQ, bad messages can be silently retried forever or lost in a noisy retry loop.

Common practice:

- set a retry limit
- move failures to DLQ
- alert on DLQ growth
- inspect poisoned messages and fix producer or consumer logic

### Idempotency in event systems

If a payment, order, or user action is triggered by an event, the consumer must be able to handle duplicate event delivery.

Example:

- event: "user created"
- consumer creates account profile
- same event is redelivered due to retry
- system must not create duplicate profile rows

The safe pattern is usually:

- unique business key
- idempotency table or unique database constraint
- durable source-of-truth record

## Security in Cloud Systems [Axer Credit, Pluxee, AppFire]

Security is not an afterthought. It is part of system design.

### Least privilege

This is the baseline principle for AWS and cloud systems.

Every identity should have the minimum required access.

Examples:

- Lambda should read only one specific S3 bucket, not all buckets
- service role should be limited to the database it needs
- admin actions should happen through a separate elevated path

### Secrets management

Never hardcode secrets in code or commit them into repositories.

Use:

- AWS Secrets Manager
- AWS Systems Manager Parameter Store
- environment injection at deploy time
- short-lived credentials where possible

### Authentication vs authorization

This distinction is critical in interviews.

Authentication is:

- verifying user identity

Authorization is:

- checking whether that identity can perform a specific action

Example:

- a user logs in with a valid JWT: authentication
- the system checks whether that JWT belongs to the same tenant and can access order 123: authorization

### OWASP-relevant risks

A cloud API must be designed against common web application risks.

Important ones:

- SQL injection: validate and parameterize queries; avoid string concatenation
- XSS: sanitize output and encode user content in UI contexts
- CSRF: use same-site cookies and anti-CSRF tokens where relevant
- SSRF: restrict outbound network access and validate external URL targets
- broken access control: enforce tenant-level and role-level checks on each action

### Tenant isolation

For multi-tenant systems, dangerous mistakes include:

- missing tenant scoping on queries
- shared caches with tenant-key leakage
- shared storage without isolation boundaries
- cross-tenant role assumptions

A resilient multi-tenant system ensures:

- tenant context is explicit in every request
- authorization checks happen at service boundaries
- secrets and configuration are isolated per tenant or environment

## Observability: Logs, Metrics, and Tracing [Axer Credit, Pluxee, AppFire]

If a system is not observable, it is not operable.

### Structured logs

Structured logs should include:

- request id
- user or tenant id when safe
- service name
- event type
- status/result
- correlation id

This makes debugging across services much easier.

### Metrics

Metrics help answer the question: "What is happening under load?"

Common metrics:

- latency
- error rate
- queue depth
- throughput
- cold start counts
- retries per dependency
- saturation and resource usage

### Distributed tracing

In a microservice or event-driven system, a single user action spans multiple services.

Tracing helps identify:

- slow dependency chains
- retries after timeout
- queue lag
- upstream/downstream bottlenecks

The key idea is correlation: a request id should travel across the system.

### Alerting and SLOs

Alerting should be based on user impact, not just raw infrastructure metrics.

Examples:

- API p95 latency above threshold for 10 minutes
- DLQ count increases above baseline
- percentage of failed checkout attempts rises
- database CPU saturation or connection pool exhaustion

A mature team uses SLOs to define what is acceptable and what needs action.

## Scalability and Reliability Patterns [Axer Credit, Pluxee, AppFire]

### Horizontal scaling

To survive load, you scale out rather than depend on a single large server.

Examples:

- multiple Lambda concurrency units
- multiple ECS tasks behind ALB
- multiple database replicas behind read traffic separation

The goal is to distribute load and reduce blast radius.

### Load balancers

Load balancers enable traffic distribution across multiple instances.

They also help with:

- health checks
- failover
- traffic splitting
- SSL termination

### Backpressure

Backpressure means the system does not accept unbounded load when downstream dependencies are struggling.

Examples:

- queueing incoming writes instead of writing directly to a slow database
- rejecting or throttling requests when the system is saturated
- capping rate per tenant or per API key

### Failure isolation

Do not let a single dependency failure take down the entire system.

Common patterns:

- separate read path and write path
- isolate background tasks from customer-facing latency
- use queues for non-critical jobs
- keep critical flow short and deterministic

## Infrastructure as Code [Axer Credit, AppFire]

Infrastructure as Code (IaC) is essential for repeatability and safe deployment.

### Terraform modules

Terraform allows teams to describe cloud resources declaratively.

Good design patterns:

- keep modules small and reusable
- separate environments like dev, staging, prod
- parameterize variables rather than hardcode values
- define outputs for dependent modules

### State management

Terraform state is critical because it tracks resource reality.

Risks:

- state corruption
- drift between infrastructure definition and actual state
- concurrent apply issues

Best practice:

- store state in a remote backend
- enable locking
- control who can change infrastructure
- regularly review drift

### Plan/apply and drift detection

A safe workflow is:

- run terraform plan
- review diffs before apply
- apply only after validation
- monitor for drift when infrastructure is externally changed

This is important because cloud systems evolve quickly and manual edits can introduce hidden instability.

## CI/CD and Rollback Strategy [Axer Credit, Pluxee, AppFire]

Cloud systems require disciplined deployment pipelines.

A typical pipeline includes:

- lint and type-check
- unit and integration tests
- security scanning
- infrastructure validation
- smoke tests or canary deployment
- production rollout

### Rollback strategy

The best rollback strategy is not just “revert commit.” It is often:

- version the deployment
- keep old artifacts available
- use traffic shifting or canary release
- validate health after rollout
- have a fast rollback path if metrics degrade

### Automated testing for infra

You should test more than application code.

Examples:

- schema migration validation
- Lambda smoke tests
- infrastructure expectation tests
- security policy checks
- API contract validation

## Containers vs Serverless [Axer Credit, Pluxee, AppFire]

This is a very common interview comparison.

### Containers

Use containers when:

- the workload is long-running or stateful
- you need custom runtime or OS-level behavior
- the application has complex dependencies
- you need predictable scaling or networking control

### Serverless

Use serverless when:

- the workload is short-lived, bursty, or event-driven
- you want to reduce operational burden
- the cost model is driven by actual usage
- there is little reason to manage machines directly

### The real answer

Containers are not automatically “better” than serverless and the reverse is also false.

The right choice depends on:

- traffic pattern
- operational skills of the team
- cost profile
- latency sensitivity
- control requirements

A strong answer often states that serverless reduces infrastructure work but introduces event-driven reasoning and observability requirements.

## Reliability Design in Practice [Axer Credit, Pluxee, AppFire]

Reliability is not a single feature. It is a system of patterns.

### Circuit breakers

If a dependency is failing repeatedly, the caller should stop hammering it and fail fast or degrade gracefully.

This protects the system from cascading failure.

### Rate limiting

Rate limiting protects downstream services and shared infrastructure from overload.

It is especially important when users are allowed to trigger expensive jobs or public APIs are exposed to large traffic volumes.

### Graceful degradation

A reliable system does not always fully succeed; it fails in a controlled way.

Examples:

- show cached data instead of making a live request
- queue a background report instead of blocking the user
- degrade recommendation features during high load

### Timeout budgets and retries with jitter

The best strategy is often:

- do not retry immediately
- use exponential backoff with jitter
- set a max retry budget
- fail to a safe state after a threshold

This avoids retry storms that make a bad event worse.

## Common Interview Framing [Axer Credit, Pluxee, AppFire]

When asked to design a cloud architecture, a good answer usually follows this structure:

1. Define the functional requirement.
2. Identify the critical user journey.
3. Define the system boundaries.
4. Choose the primary compute pattern.
5. Add eventing, queues, or async work where needed.
6. Design for retries, duplicate events, and slow dependencies.
7. Add authentication, authorization, and least-privilege policy.
8. Add observability and alerting.
9. Describe deployment strategy and rollback plan.

This structure demonstrates maturity because it shows you think in terms of resilience, not just moving code to the cloud.

## Typical Advanced Interview Questions [Axer Credit, Pluxee, AppFire]

### 1. Why not call the database directly from Lambda for everything?

Because you need to think about:

- cold starts
- connection pooling
- timeouts
- scaling behavior
- failure isolation
- event-driven processing boundaries

A database call inside a Lambda is fine for certain workloads, but it is not always the right architectural pattern for an end-to-end system.

### 2. What happens if SQS messages are duplicated?

The consumer must treat processing as idempotent. The safest pattern is a unique business identifier and a dedupe or transactional write at the time of processing.

### 3. How do you prevent a bad queue consumer from overwhelming the system?

Use queue depth monitoring, rate limiting, consumer concurrency caps, DLQs, and backpressure. You also want a dead-letter strategy and clear alerting when the queue is building up.

### 4. How do you secure a serverless API?

Use API Gateway auth, IAM roles, least privilege, secrets managers, input validation, origin restrictions, and secure tenant scoping. Do not assume serverless means automatically secure.

### 5. When is serverless a poor choice?

When the workload is long-running, latency-sensitive, resource-intensive, or requires custom networking or operating system control. In those cases, containers or VMs may be more predictable and simpler to operate.

## Final Summary [Axer Credit, Pluxee, AppFire]

The cloud architecture interview is really about resilience, security, and operational clarity.

The strongest answers emphasize:

- clear service boundaries
- async decoupling when appropriate
- retries with idempotency
- dead-letter and visibility on failures
- least-privilege security
- structured telemetry and SLO-based monitoring
- controlled deployment and rollback

If you can clearly explain how an AWS system behaves under failure, you are already thinking like a senior engineer.

## Mock Interview Questions [Axer Credit, Pluxee, AppFire]

### Question 1

Why would you choose SQS between an API and a downstream worker instead of calling the worker directly?

Expected answer:

Because it decouples the API from slow or unreliable downstream work, absorbs bursts, adds retry visibility, and prevents the user-facing request path from being blocked by expensive processing.

### Question 2

How do you handle duplicate SNS or SQS messages?

Expected answer:

Make the business side idempotent by using a unique message key or business identifier and enforce uniqueness in the database or processing state.

### Question 3

What are the key reliability concerns of Lambda?

Expected answer:

Cold starts, concurrency limits, invocation throttling, misconfigured timeouts, and failing to design for retries and duplicate execution.

### Question 4

What is the difference between authentication and authorization in AWS?

Expected answer:

Authentication verifies identity; authorization checks whether that identity is allowed to access the requested resource or action. In AWS, both are enforced by IAM, but the application should still enforce ownership and tenant-level checks.

### Question 5

How would you design a secure multi-tenant API on AWS?

Expected answer:

Use strong identity controls, least-privilege roles, VPC and network boundaries as needed, tenant-aware authorization checks, secure secret handling, and strict validation for every input and outbound request.

### Question 6

When should you prefer containers over serverless?

Expected answer:

When the workload is long-lived, needs custom OS or network behavior, has higher memory or CPU needs, or requires more control over the runtime environment than serverless provides.

### Question 7

What is better: synchronous API processing or event-driven processing?

Expected answer:

It depends on the requirement. Synchronous is better for immediate user feedback; event-driven is better for decoupling and throughput. The important part is choosing the right consistency and failure model for the business problem.
