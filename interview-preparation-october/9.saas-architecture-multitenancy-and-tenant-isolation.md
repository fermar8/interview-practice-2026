# SaaS Architecture: Multitenancy and Tenant Isolation

Scope: how SaaS systems partition data and responsibilities across tenants, how isolation is enforced, and how architecture choices affect security, migration cost, performance, and operational complexity.

## How To Use This File In Interviews

Use this file when the interviewer asks:

- "How would you design a multitenant SaaS product?"
- "How do you isolate tenant data in a shared database?"
- "What are the trade-offs between shared tables, schemas, and databases?"
- "How do you prevent one customer from seeing another customer’s data?"
- "What changes when you grow from 10 tenants to 10,000 tenants?"

The key interview theme is not just database layout. It is the combination of:

- tenancy model
- authorization model
- data isolation guarantees
- migration strategy
- operational cost and blast radius

A strong answer explains both the architecture and the trade-offs, not just the “best” model.

## What Multitenancy Really Means [Axer Credit, AppFire]

Multitenancy means multiple customers, organizations, or tenants use the same application instance while keeping their data logically separated.

The core question is:

- Is the tenant boundary enforced by application logic only?
- Is it enforced partly by the database?
- Is it enforced by completely separate infrastructure?

This matters because every tenant boundary decision affects:

- security and data leakage risk
- operational cost
- scaling and performance
- migration complexity
- how easy it is to support tenant-specific customization

## The Three Common Isolation Models [Axer Credit, AppFire]

### 1. Shared database, shared tables

In this model, all tenants use the same database and tables.

Example:

```sql
CREATE TABLE orders (
  id UUID PRIMARY KEY,
  tenant_id UUID NOT NULL,
  user_id UUID NOT NULL,
  status TEXT NOT NULL,
  total_cents BIGINT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Every query includes `tenant_id` and every application check filters by it.

This is the cheapest and easiest to operate at low scale, but it is the most vulnerable model if authorization is weak.

#### Strengths

- low infra cost
- simple deployment
- easiest to share indexes and tooling
- efficient for small and medium customer counts

#### Weaknesses

- cross-tenant leaks are possible if code forgets to filter
- harder to isolate noisy or abusive tenants
- operational risk is higher because one bad query can affect everything
- tenant-specific features are harder to implement cleanly

#### Interview expectation

If tenants share tables, you must explain how authorization is enforced in both the application and database layer.

Example patterns:

- app layer always loads data with `WHERE tenant_id = :tenantId`
- database row-level security or policies enforce tenant boundaries
- service-level checks confirm that the current user belongs to the requested tenant
- unique keys must often include `tenant_id` to prevent collision across tenants

A common interview pitfall is saying “we just filter by tenant_id” without mentioning failure modes and validation.

### 2. Shared database, separate schemas

Each tenant gets its own schema, but the database is shared.

Example:

```sql
tenant_a.orders
tenant_b.orders
tenant_c.orders
```

This gives a stronger logical boundary while still reducing infrastructure overhead.

#### Strengths

- easier to isolate by tenant at the database level
- better operational separation than a single shared table model
- simpler migration management if a tenant needs a custom schema or feature set
- lower cost than separate databases per tenant

#### Weaknesses

- still shared infrastructure and shared operational dependencies
- migrations become harder when schema changes are needed across many tenants
- one tenant’s workload can still impact the database engine overall
- data access patterns may still require tenant-aware routing logic

#### Interview expectation

You should discuss the difference between logical separation and physical isolation. Separate schemas improve boundaries, but they are not a silver bullet if the database host is still shared.

### 3. Separate databases per tenant

Each tenant or tenant group gets its own database.

This is the strongest isolation model in a typical SaaS deployment.

#### Strengths

- best data isolation and blast radius control
- easier to isolate noisy tenants
- simpler tenant-level recovery and backups
- easier to meet stricter compliance requirements

#### Weaknesses

- more infrastructure and operational overhead
- migration and deployment complexity increases
- more expensive to maintain at scale
- harder to support tenant-specific changes without careful automation

#### Interview expectation

This model is often used when a tenant has different compliance constraints, higher risk, or stronger isolation needs.

It is also a common choice for enterprise customers or larger accounts that require much tighter boundaries.

## What You Must Discuss in an Interview [Axer Credit, AppFire]

### Data leakage risk

The most important risk is accidental cross-tenant access.

Examples of dangerous patterns:

- forgetting to include `tenant_id` in a query filter
- using a global cache key like `user:123` instead of `tenant:abc:user:123`
- mixing logs and metrics across tenants without a tenant dimension
- allowing a token or session from tenant A to access tenant B resources

The architecture must assume:

- bugs happen
- queries are missed
- caches are shared incorrectly
- CI/CD may deploy a broken query

That is why defense in depth matters.

## Application-Level vs Database-Level Enforcement [Axer Credit, AppFire]

A robust SaaS design uses multiple layers.

### Application layer enforcement

The service checks that the current request is associated with the correct tenant.

Example:

```ts
const tenantId = req.user.tenantId;
const order = await db.order.findUnique({
  where: { id: orderId, tenantId },
});

if (!order) {
  throw new ForbiddenError("Order not found for this tenant");
}
```

This is necessary but insufficient on its own.

### Database layer enforcement

The database should also enforce tenant boundaries where possible.

Patterns include:

- composite keys that include tenant id
- row-level security (RLS)
- schema-level separation
- unique constraints that include tenant id
- explicit permission checks at the query layer

This reduces the chance that a single developer mistake becomes a production leak.

### Why defense in depth matters

If the app layer fails, the database should still help protect data.

If the database has a bug or a new migration is unsafe, the application should still enforce the business rule.

A secure SaaS product is not built on a single guardrail; it is designed with layers.

## Authorization Boundaries and the Tenant Context [Axer Credit, AppFire]

Tenant identity must be part of the access model.

Every request should carry enough identity data to answer:

- which tenant does this user belong to?
- which tenant is this resource associated with?
- is this action allowed for this tenant?
- is this user allowed to act on that tenant resource?

### Example tenant-aware access model

```ts
const tenantScope = req.user.tenantId;

if (resource.tenantId !== tenantScope) {
  throw new ForbiddenError("Cross-tenant access denied");
}
```

This is simple but critical. In interviews, mention that authorization is not just “is the user logged in?” but “does the tenant context match the resource context?”

## Tenant Isolation Patterns in Practice [Axer Credit, AppFire]

### Shared database, shared tables

Best when:

- there are many small tenants
- tenant data is relatively low volume
- operational simplicity matters more than strong isolation
- the SaaS product is still early stage

Common implementation details:

- every table includes `tenant_id`
- every index includes tenant id for locality and query selectivity
- cross-tenant queries are blocked by application and DB checks
- tenant-aware cache keys and logs are enforced

### Shared database, separate schemas

Best when:

- tenant separation needs to be stronger than a single table approach
- some tenants require isolated migrations or custom features
- operational cost has to be kept under control

Typical uses:

- ERP-like multi-tenant systems
- different compliance categories or customer tiers
- partial customization by tenant group without creating full per-tenant environments

### Separate databases per tenant

Best when:

- there are a few large, high-value customers
- the risk of leakage is exceptionally high
- individual customers need stronger control over their environment
- separate backups, restores, and operational policies are necessary

This model becomes expensive at scale, so it is usually selective rather than universal.

## Scalability and Tenant Isolation [Axer Credit, AppFire]

As the number of tenants grows, the isolation model also affects scaling.

### Shared table problems at scale

As tenants grow:

- indexes become bigger
- row counts increase
- hot partitions can appear
- cache invalidation becomes harder
- noisy-neighbor issues become more noticeable

A tenant with heavy usage can degrade the shared database for others.

This is called noisy-neighbor risk.

### Isolation reduces noisy-neighbor risk

Models with schema or database separation help isolate workloads.

Examples:

- a large enterprise tenant can have its own database cluster
- a low-volume tenant can stay in a shared pool
- a data-intensive tenant can get vertical isolation or dedicated storage

In a well-designed SaaS product, not every tenant has the same infrastructure profile.

## Migration and Schema Evolution in Multitenant Systems [Axer Credit, AppFire]

This is one of the most overlooked interview topics.

### Shared schema migrations

In a shared table model, schema changes affect every tenant at once.

Risk:

- migration breaks assumptions used by all tenants
- index creation or table alteration may lock a large table
- features may need gradual rollout

Best practice:

- use backward-compatible schema changes
- deploy code that can handle both old and new schema shapes
- make major changes incremental

### Per-schema or per-database migrations

In schema-separated or per-tenant DB models, migration complexity is higher because you may need to update many databases or schemas.

You need:

- orchestration for tenant-by-tenant migration
- version tracking per tenant
- safe rollout and rollback paths
- compatibility between application versions and database versions

This is often the point where architecture decisions become operational realities.

## Multi-Tenant Caching and Data Access [Axer Credit, AppFire]

Caches are often the source of subtle cross-tenant leakage.

Unsafe cache patterns:

- key = `userId` instead of `tenantId:userId`
- global in-memory store with no tenant namespace
- shared CDN cache containing tenant-specific content without a tenant key
- shared Redis keys used by multiple tenants

Safe patterns:

- `tenant:{tenantId}:user:{userId}`
- region, tenant, and role-specific cache namespaces
- tenant-aware object serialization and auth checks
- cache invalidation strategy that respects tenant boundaries

In interviews, say that caching is not just about speed—it is also a data isolation problem.

## Tenant-Specific Features and Configuration [Axer Credit, AppFire]

A SaaS product often needs tenant-specific configuration.

Examples:

- billing plan or limits
- custom permissions and roles
- feature flags
- region preferences
- SSO config
- custom branding and theme

The architecture should support this without making the codebase unsafe.

Patterns:

- store tenant config in a dedicated table or service
- attach tenant context to every request
- enforce feature checks at the API layer
- keep tenant-specific policy logic centralized and auditable

This is also where “authz by config” often fails if configuration is not locked to tenant context.

## Security and Compliance Considerations [Axer Credit, AppFire]

For multitenant systems, security concerns extend beyond user auth.

### Data export and recovery

If a tenant requests a data export or deletion, it must be restricted to that tenant’s data only.

### Backups and restore

Tenants may need isolation in backups, restore procedures, and disaster recovery plans.

### Audit logs

Audit logs should include:

- tenant id
- actor id
- action type
- object id
- timestamp
- result

This supports incident response and compliance review.

### Data residency

Some organizations require data to stay in a certain region or country.

This pushes architecture toward:

- regional tenant partitions
- stricter isolation
- more careful routing logic

## Common Interview Questions and Strong Answers [Axer Credit, AppFire]

### Question 1

What are the main multitenancy models?

Strong answer:

The main models are shared database/shared tables, shared database/separate schemas, and separate databases per tenant. Each model trades off isolation, cost, complexity, and operational overhead. Shared tables are cheapest but highest risk; separate databases are the strongest isolation but hardest to operate at scale.

### Question 2

How do you prevent cross-tenant data access?

Strong answer:

I enforce tenant context at every boundary: the request carries user and tenant identity, the application checks resource ownership, the database enforces tenant-scoped queries, and cache keys and logs are tenant-aware. I also add row-level security or unique constraints that include tenant id where possible.

### Question 3

When would you choose separate databases per tenant?

Strong answer:

When a tenant has stricter compliance needs, higher blast radius risk, or significantly different resource usage patterns. It is useful when strong isolation is worth the higher operational cost.

### Question 4

What is the biggest risk in a shared-table SaaS design?

Strong answer:

The biggest risk is accidental cross-tenant leakage through missing tenant filters, unsafe caching, or authorization mistakes. Shared-table models are fine if there are strong guardrails, but they are sensitive to developer error.

### Question 5

How do noisy neighbors affect multitenant systems?

Strong answer:

A noisy neighbor is one tenant that consumes disproportionate resources and degrades performance for others. Shared infrastructure amplifies this issue. Strong isolation, quoting, rate limiting, and dedicated resources are the usual mitigations.

## Final Takeaway [Axer Credit, AppFire]

The best SaaS architecture is not defined by one universal isolation pattern. It is defined by matching the model to the product’s risk, growth, compliance, and operational needs.

In interviews, the strongest answer usually includes:

- the tenant model
- how authorization is enforced
- how failure and leakage are prevented
- how the system scales with many tenants
- how migrations and feature rollout remain safe

If you can explain the trade-offs clearly and show you understand that security and operations are part of the design, you will sound senior and practical.

## Mock Interview Questions [Axer Credit, AppFire]

### Question 1

Would you prefer a shared database with shared tables or separate databases per tenant for a new SaaS startup?

Expected answer:

For a new startup, shared database/shared table is often the right starting point because it is cheaper and easier to operate. But the system must enforce tenant context in every access path. As the product grows or compliance requirements increase, the architecture may evolve toward schema or database isolation for specific tenant groups.

### Question 2

How do you handle a query bug that forgot to add `tenant_id` in a shared-table design?

Expected answer:

Use layered defense: application-level checks, database-level constraints and row-level security, audit logging, and automated tests that validate tenant-scoped access. The system should also have monitors for cross-tenant anomalies and a fast incident-response path.

### Question 3

What is the difference between logical isolation and physical isolation?

Expected answer:

Logical isolation means the platform enforces tenant boundaries using code and database rules; physical isolation means tenants are separated into different infrastructure units, such as distinct schemas or databases. Stronger physical isolation reduces blast radius but increases cost and operational complexity.

### Question 4

What are the key risks of shared cache keys in a multitenant app?

Expected answer:

Cross-tenant data leakage and stale tenant state. Every cache key should include a tenant or namespace dimension, and the architecture should validate tenant ownership before serving cached data.

### Question 5

How would you design tenant-aware authorization for an order API?

Expected answer:

The request should carry tenant context, the order resource should be looked up with both tenant and order id, and the system should deny access if the tenant context mismatches. The database should also enforce tenant scoping where possible.

### Question 6

What makes multitenancy hard as a product scales?

Expected answer:

Noisy-neighbor effects, larger indexes, migration complexity, and increased operational risk. A strong architecture plan includes growth-aware isolation, quotas, per-tenant resource policies, and careful rollout of schema changes.

### Question 7

When is schema separation a better choice than shared tables?

Expected answer:

When tenant boundaries need to be stronger, feature customizations vary significantly across customers, or operational isolation matters more than absolute simplicity. Schema separation gives better logical boundaries without the full cost of dedicated databases for every tenant.
