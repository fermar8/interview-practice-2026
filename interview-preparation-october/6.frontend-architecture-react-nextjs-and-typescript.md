# Frontend Architecture with React, Next.js, and TypeScript

Scope: Rendering models, data flow, server/client boundaries, state design, and frontend type safety.

## How To Use This File In Interviews

Use this file to answer one core question clearly:

- How do you design a frontend so that it is fast, secure, maintainable, and correct without mixing server-only logic into the browser?

Interview goal:

- Explain the difference between rendering strategies and when each one is appropriate.
- Show that you understand server/client boundaries, data fetching, caching, and auth.
- Demonstrate practical TypeScript patterns, not just abstract theory.

High-signal answer pattern:

1. Start with the user experience requirement.
2. Explain whether the work belongs on the server, client, or both.
3. Describe the data flow and caching strategy.
4. Mention security boundaries and state concerns.
5. Connect the decision back to maintainability and performance.

## React Rendering Models [Axer Credit, AppFire]

The biggest architectural decision in a modern frontend is not just "do I use React?" but rather:

- What runs on the server?
- What runs in the browser?
- What is rendered at build time, request time, or runtime?

### Server Components

Server Components are best when:

- the data is sensitive or server-only
- the component can read from the database or internal APIs directly
- the rendering can happen before the browser gets it

Example:

```tsx
// Server Component
async function UserSummary({ userId }: { userId: string }) {
  const user = await db.user.findUnique({ where: { id: userId } });

  return <div>{user?.name}</div>;
}
```

Why this matters:

- no extra API round trip for data that was already available on the server
- fewer client bundle costs
- better separation of concerns

### Client Components

Client Components are needed for:

- interactivity
- browser APIs
- local state
- effects and event handlers

Example:

```tsx
"use client";

import { useState } from "react";

export function Counter() {
  const [count, setCount] = useState(0);

  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}
```

The important interview rule:

- "Keep interactivity in Client Components and keep data fetching and secure logic on the server unless there is a real client need."

## SSR, SSG, and CSR [Axer Credit, AppFire]

### Server-Side Rendering (SSR)

The server renders the HTML on each request.

Good for:

- personalized or frequently changing pages
- authenticated content
- content that depends on request-time data

Example use cases:

- dashboards
- user-specific profile pages
- recent or time-sensitive content

### Static Site Generation (SSG)

The HTML is generated at build time or revalidated later.

Good for:

- marketing pages
- docs
- product pages with infrequent change

Example pattern:

```tsx
export const revalidate = 3600;
```

### Client-Side Rendering (CSR)

A page loads a shell and then fetches data in the browser.

Good for:

- highly interactive apps
- complex UI state management
- client-driven flows

Bad for:

- SEO-sensitive content
- user-specific data that should not be exposed to the client

### Interview framing

- "The right strategy depends on whether the page is primarily static, request-specific, or interactive. The rendering model should match the real use case, not the default framework pattern."

## Next.js Data Flow Patterns [Axer Credit, AppFire]

### Route Handlers

Use Route Handlers for server-side API endpoints inside the app.

Example:

```ts
// app/api/users/route.ts
import { NextResponse } from "next/server";

export async function GET() {
  return NextResponse.json({ ok: true });
}
```

Use this when:

- the request belongs to the app backend
- you need server-side validation or secure logic
- the data is not meant to be exposed directly to the client as a public API

### Server Actions

Server Actions are useful for form submissions and server-side state transitions.

Example:

```tsx
"use server";

export async function createProject(formData: FormData) {
  const name = formData.get("name");
  // validate, persist, redirect
}
```

Use this when:

- the mutation is tightly coupled to the current page flow
- the server can validate and then redirect or revalidate
- you want to keep the client side simple

### Conventional API vs Server Action

Prefer a Server Action when:

- it is a same-page mutation
- the server owns the business logic
- you want form behavior and validation in one place

Prefer a Route Handler or external API when:

- you need a reusable API contract
- multiple clients or services will call it
- you want a formal public interface

### Interview answer pattern

- "If the interaction is part of a user flow and the logic is server-owned, I prefer a Server Action. If it is a reusable API contract, I prefer an endpoint or service API."

## Data Fetching, Caching, and Revalidation [Axer Credit, AppFire]

### Fetching in Next.js

The server can fetch data directly as part of rendering. This reduces unnecessary client requests and keeps the app more predictable.

Example:

```tsx
async function ProductsPage() {
  const products = await fetch("https://api.example.com/products", {
    cache: "no-store",
  });

  return <ProductList products={await products.json()} />;
}
```

### Cache policy choices

- `cache: 'force-cache'`: reuse cached data when possible
- `cache: 'no-store'`: always fetch fresh data
- `revalidate`: refresh based on time or on-demand invalidation

Typical patterns:

- static content: longer cache TTL
- user-specific pages: short or `no-store`
- sensitive data: always fresh

### Revalidation

Revalidation updates or invalidates stale cached data after a mutation.

Example:

```tsx
export const revalidate = 60;
```

This keeps the app consistent without requiring manual full-page refreshes.

### Cache invalidation problems

The real risk is not just stale data; it is incorrect stale data.

Examples:

- user profile cached after role change
- product inventory cache not cleared after stock update
- list of invoices cached after a status transition

The system needs a clear invalidation policy:

- invalidate on mutation
- revalidate on write events
- use tags or keys that match the real data ownership

### Strong interview answer

- "Caching without invalidation is a correctness bug, not a performance optimization."

## State Management and Forms [Axer Credit, AppFire]

Frontend state is about balancing local state, server state, and user interaction.

### Local UI state

Use React state for:

- form inputs
- modal visibility
- toggles
- transient UI detail

Example:

```tsx
const [isOpen, setIsOpen] = useState(false);
```

### Server state

Server state is usually remote data and should be treated differently from UI state.

Examples:

- user list from API
- product catalog
- dashboard metrics

Typical patterns:

- React Query / TanStack Query
- server cache + revalidation
- optimistic updates with rollback logic

### Forms and loading states

Forms need:

- validation
- disabled states
- loading indicators
- error boundaries or user-friendly error messages

Example:

```tsx
const [isSubmitting, setIsSubmitting] = useState(false);
const [error, setError] = useState<string | null>(null);
```

A good form UX is not just about submitting data; it is about handling in-flight state and failure gracefully.

### Error handling

Never treat error states as an afterthought.

Examples:

- validation error on submit
- request timeout while saving
- stale cache while revalidation runs
- unauthorized request from a protected route

Use clear boundaries:

- client validation for fast feedback
- server validation for correctness
- user-visible retry and recovery flows

## Authentication and Authorization [Axer Credit, AppFire]

### Authentication

Authentication answers: "Who is this user?"

This is usually handled by a session, token, or auth provider.

### Authorization

Authorization answers: "What is this user allowed to do?"

This must be enforced on the server, not only in the browser.

Bad approach:

```tsx
if (user?.role === "admin") {
  // render admin UI
}
```

Why it is bad:

- the browser can be manipulated
- the data can still be fetched or mutated by a malicious client
- authorization must live where the data and business logic are trusted

Correct approach:

- server validates identity and permissions
- server-only data is never exposed without checks
- client only sees what it is allowed to see

### Protecting server-only data

Examples:

- database rows not visible to a user
- internal analytics endpoints
- admin-only operations

The rule is simple:

- do not trust client-side UI gates as the source of truth

## TypeScript in React [Axer Credit, AppFire]

TypeScript adds a lot of value when used honestly.

### Generics

Generics are useful when components or utilities need to work with different data shapes while preserving type safety.

Example:

```ts
type ApiResponse<T> = {
  data: T;
  error?: string;
};
```

### Discriminated unions

This is one of the best TypeScript patterns in frontend code.

Example:

```ts
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string[] }
  | { status: "error"; message: string };
```

This makes UI handling far easier and more reliable.

### Utility types

Examples:

- `Partial<T>`
- `Pick<T, K>`
- `Omit<T, K>`
- `Record<K, T>`
- `Readonly<T>`

These make API model transformations cleaner and safer.

### Narrowing

TypeScript narrowing is essential in React UIs.

Example:

```ts
if ("message" in error) {
  console.log(error.message);
}
```

This prevents brittle casts and keeps components type-safe.

## Common Frontend Architecture Mistakes [Axer Credit, AppFire]

- Putting sensitive logic in the browser because it is "easy to do".
- Fetching the same data repeatedly instead of using caching and revalidation.
- Treating stale cache as harmless when the data is user-critical.
- Mixing server-only concerns with Client Components.
- Using overly broad state stores when local component state is enough.
- Ignoring loading and error states in real user flows.

## Deep Mock Questions Focused On This File [Axer Credit, AppFire]

### 1) "When do you choose Server Components over Client Components?"

Strong answer:

- when the data is server-owned or sensitive
- when the component can render without browser interactivity
- when avoiding extra client-side data fetching is important

### 2) "What is the difference between SSR, SSG, and CSR?"

Strong answer:

- SSR renders per request
- SSG renders ahead of time and reuses content
- CSR renders after the browser loads

Each is suited to different content freshness and interaction needs.

### 3) "Why is cache invalidation a correctness problem?"

Strong answer:

- because stale cache can serve wrong data to users
- because data can be inconsistent across pages and systems
- because invalidation has to match business semantics, not just API semantics

### 4) "Why should authorization not live only in the client?"

Strong answer:

- the client is not trusted
- malicious requests can bypass the UI
- protected data must be checked server-side before it is returned

### 5) "How do discriminated unions help in React apps?"

Strong answer:

- they model state transitions explicitly
- UI can branch on `status`
- the type system helps prevent invalid combinations and broken render states

### 6) "When would you use a Server Action instead of a Route Handler?"

Strong answer:

- when the mutation is part of a page interaction and the server owns the business logic
- when you want to keep the client flow simple and the server validation centralized
- when you are not exposing a reusable public API contract

### 7) "What is the real trade-off of React server/client boundaries?"

Strong answer:

- better separation of responsibilities and security
- more careful design of data passing and component boundaries
- the cost is more architecture discipline and less implicit behavior

### 8) "What is a common mistake in Next.js caching?"

Strong answer:

- assuming the cache is automatically correct
- not invalidating after writes
- using broad cache strategies without thinking about user freshness and data ownership

## 60-Second Interview Summary [Axer Credit, AppFire]

"A strong React and Next.js architecture is about deciding which work belongs on the server, which work belongs in the browser, and how data moves between them. I prefer server-owned logic and secure data access, use client components only for interactivity, and choose SSR, SSG, or CSR based on freshness and user needs. TypeScript patterns like discriminated unions and generic models help keep UI state and API flows safe and maintainable, while caching and invalidation policies are essential if the app is going to stay fast without becoming stale or insecure."
