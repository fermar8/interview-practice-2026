## Encapsulation (Deep) [Axer Credit, AppFire]

### What It Is

Encapsulation is enforcing invariants by controlling state transitions through explicit behaviors.

Strong interview framing:

- "I treat state as a protected asset and expose domain operations, not raw mutation."

### Why It Matters In Real Systems

- Prevents illegal states (for example negative balances).
- Centralizes business rules.
- Improves auditability because state changes happen through known entry points.

### Good Example

```ts
class Wallet {
  private balanceCents = 0;

  deposit(amountCents: number): void {
    if (amountCents <= 0) throw new Error("Amount must be positive");
    this.balanceCents += amountCents;
  }

  withdraw(amountCents: number): void {
    if (amountCents <= 0) throw new Error("Amount must be positive");
    if (amountCents > this.balanceCents) throw new Error("Insufficient funds");
    this.balanceCents -= amountCents;
  }

  getBalanceCents(): number {
    return this.balanceCents;
  }
}
```

### Anti-Pattern

- Exposing public mutable state (`wallet.balanceCents = -100`) bypasses rules and causes hidden corruption.

### Interview Follow-Up You Should Be Ready For

Q: "Is private field enough for true safety?"
A: "No. Private fields protect in-process mutation, but cross-request correctness still needs transactional boundaries and database constraints."

## Composition vs Inheritance (Deep) [Axer Credit, AppFire]

### Core Decision Rule

- Prefer composition by default.
- Use inheritance only when subtype semantics are stable and true substitutability holds.

### Composition Example

```ts
interface TaxPolicy {
  calculate(amountCents: number): number;
}

class FlatTaxPolicy implements TaxPolicy {
  constructor(private readonly rate: number) {}

  calculate(amountCents: number): number {
    return Math.floor(amountCents * this.rate);
  }
}

class InvoiceService {
  constructor(private readonly taxPolicy: TaxPolicy) {}

  total(baseCents: number): number {
    return baseCents + this.taxPolicy.calculate(baseCents);
  }
}
```

Why this scales:

- New policy does not require editing `InvoiceService`.
- Test matrix is smaller and behavior is isolated.

### When Inheritance Is Acceptable

- Domain has a stable hierarchy.
- Child does not weaken parent contract.
- Overridden behavior remains unsurprising.

### Red Flags

- Child classes override most parent behavior.
- Many protected fields leak implementation details.
- "Base class" changes frequently and breaks children.

### Strong Interview Line

"I choose composition unless I can prove inheritance improves clarity without coupling the future to parent internals."

## SOLID (Applied, Not Dogmatic) [Axer Credit, AppFire]

### S: Single Responsibility

Question to ask:

- "What distinct business reason would force this class to change?"

Smell:

- Class does validation, business logic, database IO, and notifications together.

### O: Open/Closed

Target behavior:

- Add new behavior through new implementations, not edits to core stable logic.

Smell:

- Adding one provider requires editing switch statements across many modules.

### L: Liskov Substitution

Rule:

- Subtype must honor parent expectations and invariants.

Smell:

- Subtype throws "not supported" for parent methods.

### I: Interface Segregation

Rule:

- Smaller role-based interfaces beat one giant interface.

Smell:

- Implementers depend on methods they do not need.

### D: Dependency Inversion

Rule:

- Business logic depends on abstractions; details implement those abstractions.

Smell:

- Service imports concrete ORM models and third-party SDK clients directly.

### Senior-Level Way To Talk About SOLID

"I use SOLID as a refactoring compass. If changes spread too far or tests become expensive, a principle is usually being violated."

## Separation of Concerns (SoC) [Axer Credit, AppFire]

### Practical Layering

- Controller: transport and request/response concerns.
- Service: business rules and orchestration.
- Repository: persistence concerns.
- Gateway/Adapter: external provider concerns.

### Why This Is Valuable

- Failures are easier to localize.
- Unit tests stay fast because domain logic is isolated.
- Integration tests become intentional boundary checks.

### Anti-Pattern To Avoid

- "Fat controller": validation, SQL, retries, and provider calls in one method.

### Interview-Quality Refactor Narrative

"I moved provider-specific retry logic from controller to gateway adapter, kept business policy in service, and reduced controller to input/output mapping. That reduced duplicate retry bugs and made provider-specific tests independent."

## Dependency Inversion (Deep) [Axer Credit, AppFire]

### Core Idea

High-level policy should not know low-level implementation details.

### Example

```ts
interface PaymentRepository {
  save(tx: { id: string; amountCents: number }): Promise<void>;
}

interface PaymentGateway {
  authorize(amountCents: number): Promise<{ approved: boolean }>;
}

class PaymentService {
  constructor(
    private readonly repo: PaymentRepository,
    private readonly gateway: PaymentGateway,
  ) {}

  async createPayment(id: string, amountCents: number): Promise<void> {
    if (amountCents <= 0) throw new Error("Amount must be positive");

    const result = await this.gateway.authorize(amountCents);
    if (!result.approved) throw new Error("Payment rejected");

    await this.repo.save({ id, amountCents });
  }
}
```

### Testability Benefit

```ts
class InMemoryPaymentRepository implements PaymentRepository {
  public readonly data: { id: string; amountCents: number }[] = [];

  async save(tx: { id: string; amountCents: number }): Promise<void> {
    this.data.push(tx);
  }
}

class AlwaysApproveGateway implements PaymentGateway {
  async authorize(): Promise<{ approved: boolean }> {
    return { approved: true };
  }
}
```

This allows fast policy tests without network/database setup.

### Trade-Off You Should Mention

- More interfaces and wiring can add boilerplate.
- Worth it when domain volatility and integration complexity are high.

## Deep Mock Questions (Only Requested Topics) [Axer Credit, Pluxee, AppFire]

### 1) "Explain encapsulation beyond 'private fields'."

Strong answer:

- Encapsulation is about protecting invariants through controlled transitions.
- Private fields are just one mechanism.
- Real safety also requires transactional consistency and validation at boundaries.

### 2) "When is inheritance the wrong choice?"

Strong answer:

- When behavior variation is frequent and cross-cutting.
- When child classes override parent behavior heavily.
- When the hierarchy forces unrelated features to couple.

### 3) "How do SOLID and SoC help incident response?"

Strong answer:

- Clear boundaries narrow blast radius and speed diagnosis.
- You can isolate whether failure is transport, policy, persistence, or provider integration.
- Rollbacks become more surgical.

### 4) "What is a practical DIP example from backend APIs?"

Strong answer:

- Service depends on `PaymentGateway` interface.
- Stripe/Adyen implementations sit behind adapters.
- New provider integration does not require business-rule rewrites.

### 5) "How do you avoid over-abstracting with DIP?"

Strong answer:

- I introduce abstractions where volatility exists (external dependencies, persistence, policies).
- I avoid speculative interfaces with no plausible alternate implementation.
- I periodically remove unused abstractions.

### 6) "Give a bad answer and strong answer for composition vs inheritance."

Bad answer:

- "Composition is always better."

Strong answer:

- "Composition is my default because it reduces coupling and makes behavior replaceable. I choose inheritance only when subtype semantics are stable and substitutable."

### 7) "How do you prove Separation of Concerns in a code review?"

Strong answer:

- I check if each layer can be tested independently.
- I verify controllers contain no business rules.
- I verify services are not coupled to transport or ORM specifics.

### 8) "How would you refactor a fat class violating Single Responsibility Principle?"

Strong answer:

- Split responsibilities by reason-to-change.
- Extract policy logic, persistence, and integrations.
- Add thin orchestration service.
- Keep behavior identical with characterization tests before refactor.

### 9) "What does Liskov violation look like in practice?"

Strong answer:

- Child weakens preconditions or breaks postconditions.
- Example: parent `withdraw` guarantees non-negative balance, child allows overdraft silently.
- Consumers relying on parent contract break unexpectedly.

### 10) "How do you summarize these principles in one minute?"

Strong answer:

- "I use encapsulation to protect invariants, composition to keep behavior flexible, SOLID as a changeability diagnostic, separation of concerns to keep boundaries clean, and dependency inversion to keep core policy independent from infrastructure. The result is code that is easier to test, safer to change, and faster to debug in production."
