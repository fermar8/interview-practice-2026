## Node.js Runtime And Async Execution [Axer Credit, Pluxee, AppFire]

### Event Loop Basics That Matter In Interviews

What interviewers want:

- You understand that Node.js is single-threaded for JavaScript execution.
- You understand concurrency comes from the event loop + non-blocking I/O.
- You can identify blocking code that hurts throughput.

Strong explanation:

- CPU-heavy synchronous work blocks the event loop.
- I/O callbacks/promises are scheduled and executed later.
- Long event-loop stalls increase latency for all requests.

### Blocking vs Non-Blocking Example

```ts
import { readFile } from "node:fs/promises";

// Good: non-blocking I/O with await
export async function loadConfig(path: string): Promise<string> {
  return await readFile(path, "utf8");
}

// Bad in hot paths: blocks event loop for all concurrent requests
export function expensiveSyncLoop(items: number[]): number {
  let sum = 0;
  for (const n of items) {
    for (let i = 0; i < 200_000; i++) sum += n;
  }
  return sum;
}
```

Real-life scenario:

- A synchronous JSON transformation inside an API route can spike p99 latency under load because it blocks unrelated requests.

### Promise Concurrency Patterns

Use the right pattern for the job:

- Sequential dependency: `await a(); await b();`
- Independent calls: `await Promise.all([a(), b()])`
- Partial tolerance: `Promise.allSettled`

```ts
async function loadDashboard(userId: string) {
  const [profile, invoices] = await Promise.all([
    getProfile(userId),
    getInvoices(userId),
  ]);

  return { profile, invoices };
}
```

Interview pitfall:

- Using `await` in a loop when operations are independent and can run concurrently.

## Error Propagation In Async Code [Axer Credit, Pluxee, AppFire]

### Runtime Reality

In async systems, errors happen at boundaries:

- Network timeouts
- Provider failures
- Validation failures
- Unexpected exceptions

Strong backend pattern:

- Convert unknown exceptions into typed/known errors at service boundaries.
- Keep transport-specific mapping in controller/exception filter.

```ts
class DomainError extends Error {
  constructor(
    public readonly code: "NOT_FOUND" | "CONFLICT" | "INVALID",
    message: string,
  ) {
    super(message);
  }
}

async function findUserOrThrow(userId: string) {
  const user = await userRepo.findById(userId);
  if (!user) throw new DomainError("NOT_FOUND", "User does not exist");
  return user;
}
```

What to say in interviews:

- "I separate domain errors from infrastructure errors, then map domain errors to consistent HTTP responses."

### Unhandled Rejection Awareness

You should mention:

- Every promise should be awaited or explicitly handled.
- Background async work should have failure logging and retry policy.

## TypeScript Type Narrowing And Runtime Validation [Axer Credit, Pluxee, AppFire]

### Why Type Narrowing Is Not Enough Alone

TypeScript checks compile-time assumptions.
External input still requires runtime validation.

### Narrowing Example

```ts
type CreateUserInput = {
  email?: unknown;
  age?: unknown;
};

function isString(v: unknown): v is string {
  return typeof v === "string";
}

function isNumber(v: unknown): v is number {
  return typeof v === "number" && Number.isFinite(v);
}

function parseCreateUser(input: CreateUserInput): {
  email: string;
  age: number;
} {
  if (!isString(input.email)) throw new Error("email must be a string");
  if (!isNumber(input.age)) throw new Error("age must be a number");
  if (input.age < 18) throw new Error("age must be >= 18");

  return { email: input.email, age: input.age };
}
```

Interview-quality takeaway:

- "Narrowing protects internal logic, runtime validation protects trust boundaries."

## NestJS Architecture: Practical Reasoning [Axer Credit, Pluxee]

### Modules

Purpose:

- Define feature boundaries.
- Control provider visibility.

What to say:

- "I organize by domain features, not technical folders only."

### Providers And Dependency Injection

Why it matters:

- Testability through replaceable dependencies.
- Clear contracts between layers.

```ts
import { Injectable } from "@nestjs/common";

@Injectable()
export class BillingService {
  constructor(private readonly paymentsClient: PaymentsClient) {}

  async charge(userId: string, amountCents: number) {
    return await this.paymentsClient.charge(userId, amountCents);
  }
}
```

### Controllers

Controller role:

- Map HTTP in/out.
- Delegate policy decisions to services.

Controller anti-pattern:

- Complex business logic, retries, and SQL in controller methods.

### Guards, Interceptors, Exception Filters

Guard:

- Access control before handler execution.

Interceptor:

- Cross-cutting behavior (logging, timing, response shaping).

Exception filter:

- Centralized exception-to-response mapping.

```ts
import {
  CanActivate,
  ExecutionContext,
  Injectable,
  NestInterceptor,
  CallHandler,
} from "@nestjs/common";
import { Observable } from "rxjs";
import { tap } from "rxjs/operators";

@Injectable()
export class ApiKeyGuard implements CanActivate {
  canActivate(ctx: ExecutionContext): boolean {
    const req = ctx.switchToHttp().getRequest();
    return req.headers["x-api-key"] === process.env.API_KEY;
  }
}

@Injectable()
export class TimingInterceptor implements NestInterceptor {
  intercept(_: ExecutionContext, next: CallHandler): Observable<unknown> {
    const start = Date.now();
    return next
      .handle()
      .pipe(tap(() => console.log("duration_ms", Date.now() - start)));
  }
}
```

Strong interview line:

- "I keep auth policy in guards, business logic in services, and cross-cutting telemetry in interceptors."

## API Versioning And Backward Compatibility [Axer Credit, Pluxee, AppFire]

### Versioning Strategy

Common strategies:

- URI versioning: `/v1/users`
- Header versioning: `Accept-Version: 2`

What matters most:

- Clear deprecation lifecycle.
- Contract stability for existing clients.

### Backward Compatibility Rules

Safe changes:

- Add optional response fields.
- Add new optional request fields.

Risky/breaking changes:

- Rename/remove existing fields.
- Change field meaning/type.
- Change error contract without migration plan.

### Compatibility Example

```ts
type UserV1 = { id: string; name: string };
type UserV2 = { id: string; fullName: string; locale?: string };

function toV1(v2: UserV2): UserV1 {
  return { id: v2.id, name: v2.fullName };
}
```

Interview-quality phrasing:

- "I treat API responses as public contracts. Internal refactors are free; contract breaks are not."

## Deep Mock Questions Focused On This File [Axer Credit, Pluxee, AppFire]

### 1) "What does 'Node is single-threaded' actually imply for API latency?"

Strong answer:

- JavaScript execution runs on one thread, so CPU-heavy synchronous work blocks all in-flight request handlers.
- Non-blocking I/O enables concurrency, but CPU bottlenecks still hurt throughput and p99.
- Mitigations include chunking CPU work, moving heavy tasks to workers/queues, and avoiding sync hot-path operations.

### 2) "When should you use Promise.all vs sequential await?"

Strong answer:

- `Promise.all` for independent tasks where total latency should be minimized.
- Sequential awaits when task B depends on A or when rate limiting/order matters.
- I mention failure behavior: one rejection fails `Promise.all`, while `allSettled` supports partial success scenarios.

### 3) "How do you structure async error handling in a NestJS service?"

Strong answer:

- Service throws domain-specific errors.
- Controller/filter maps these to HTTP responses.
- Unknown infrastructure errors are logged with request correlation and converted to safe error responses.

### 4) "Why is TypeScript not enough for request safety?"

Strong answer:

- Types are erased at runtime.
- External payloads are untrusted and need runtime validation.
- I validate at boundary, then pass strongly typed data to domain logic.

### 5) "What belongs in guard vs interceptor vs controller?"

Strong answer:

- Guard: authorization/admission control.
- Controller: transport mapping and delegation.
- Interceptor: cross-cutting concerns like logging/metrics/response mapping.
- Business rules stay in service.

### 6) "How do you introduce v2 without breaking v1 clients?"

Strong answer:

- Keep v1 stable during deprecation window.
- Add translation/adapters where needed.
- Publish migration notes and monitor v1 usage before removal.
- Avoid hidden behavior changes under same version.

### 7) "What is a common NestJS anti-pattern in interviews?"

Strong answer:

- Fat controllers with business logic and data access.
- It weakens testability and separation of concerns.
- Refactor by moving orchestration/policy to providers and keeping controllers thin.

### 8) "How do you discuss backward compatibility trade-offs honestly?"

Strong answer:

- Supporting old versions increases maintenance cost.
- Breaking changes reduce complexity but can damage client trust.
- I prefer planned deprecation with telemetry-driven retirement.

## Common Mistakes To Avoid [Axer Credit, Pluxee, AppFire]

- Confusing asynchronous with parallel.
- Using TypeScript types as if they validate runtime payloads.
- Catching all errors and returning generic responses without observability.
- Putting business logic in NestJS controllers.
- Shipping breaking API changes without explicit version migration.

## 60-Second Interview Summary [Axer Credit, Pluxee, AppFire]

"In Node.js backends, I optimize for event-loop health, explicit async error handling, and clear boundary validation. I use TypeScript narrowing for internal safety and runtime validation for external inputs. In NestJS, I keep controllers thin, business logic in providers, auth in guards, and cross-cutting concerns in interceptors/filters. For API evolution, I use versioning and compatibility rules so clients can migrate predictably without surprise breaks."
