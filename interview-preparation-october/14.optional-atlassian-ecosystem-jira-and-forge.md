## Jira Workflows: The Core Concept [Pluxee, AppFire]

A Jira workflow defines the lifecycle of an issue.

Typical workflow states include:

- To Do
- In Progress
- In Review
- Done

Transitions define how an issue moves between states.

Examples:

- from To Do to In Progress
- from In Progress to In Review
- from Review to Done
- from In Review to In Progress for rework

### Why workflows matter

Workflows encode process discipline.

They help with:

- consistent process across teams
- automation based on status
- visibility into bottlenecks
- enforcement of approval or quality gates

A senior product-minded engineer understands that workflows are not just UI labels. They are operational policy.

## Workflow Conditions and Validators [Pluxee, AppFire]

These are two of the most important concepts for Jira automation.

### Conditions

A condition controls whether a transition is allowed at all.

Example:

- only allow an issue to move to Done if the issue has at least one linked fix version
- only allow a transition if the user has the correct project role

This is a gate.

### Validators

A validator checks the issue data before allowing a transition.

Examples:

- ensure a required custom field is filled
- verify that an issue has a due date before marking it done
- ensure a comment is added when moving to a blocked state

This is a data-quality check.

### Why this matters in product design

These mechanisms show that workflow tools can enforce policy, not just move tickets around. That is a good product and operations lesson.

## Custom Fields [Pluxee, AppFire]

Custom fields extend Jira with domain-specific information.

Examples:

- environment
- customer impact
- release train
- severity classification
- deployment status
- support contract tier

Custom fields matter because they let process rules become data-driven.

For example:

- a validation can require an Environment field before moving an incident to Resolved
- a workflow can branch logic differently based on a Severity custom field

The important design insight is this:

- workflows define process steps
- custom fields define the data that drives process decisions

## Forge Apps and the Atlassian Cloud Ecosystem [AppFire]

Forge is Atlassian’s app platform for building extensions in the Atlassian Cloud ecosystem.

A Forge app can provide:

- custom UI in Jira
- automation or app triggers
- integrations with Jira data
- new admin or user experiences
- issue-side or project-side capabilities

### What matters more than the framework

The important product question is:

- what problem is this app solving for users and teams?

For example:

- automate handoff between development and support
- surface release risk information inline in Jira
- enforce process policy with better UX than native workflow steps alone

The framework itself is secondary if the product need is unclear.

## Understanding the Product Problem First [Pluxee, AppFire]

This is the best advice for Atlassian ecosystem work.

Before learning Forge specifics, ask:

- what workflow is broken?
- where does process friction occur?
- who is blocked by the current state?
- what is the business or operational pain?
- could a custom field or workflow rule solve it without building a full app?

This helps avoid overbuilding.

A good answer in an interview is often:

- start with the workflow and process problem
- then decide whether Jira-native features are enough
- only then consider a Forge app or deeper extension

## Typical Questions [Pluxee, AppFire]

### Question 1

What is a Jira workflow?

Expected answer:

A workflow is the sequence of states and transitions an issue moves through as it progresses from creation to completion.

### Question 2

What is the difference between a condition and a validator?

Expected answer:

A condition decides whether a transition is allowed at all. A validator checks that required data exists or meets constraints before transition completion.

### Question 3

Why are custom fields useful?

Expected answer:

They capture workflow-specific data so process rules can be automated and enforced based on real business context.

### Question 4

When would you build a Forge app instead of using Jira-native features?

Expected answer:

When the process requires custom interaction, additional data handling, or a product experience beyond what native workflows and fields provide.

### Question 5

What is the most important thing to understand before building an Atlassian app?

Expected answer:

The real user and product problem. Framework details matter much less than whether the app actually reduces friction or enforces process correctly.
