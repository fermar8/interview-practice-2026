## Quick Definition Cheat Sheet

- Throttling: a service refuses new work because the system has hit a concurrency, rate, or capacity limit. In Lambda, this usually means the function, account, or region cannot start additional executions.
- Event loop: the mechanism Node.js uses to schedule and process async work without blocking the main thread; it is ideal for I/O-heavy workloads but not for long CPU-bound operations.
- Garbage collection: the runtime process that reclaims memory no longer reachable by the application. High GC pressure often increases latency and CPU usage.
- Reserved concurrency: the maximum number of Lambda executions allowed to run at the same time for a specific function, used to protect other functions from being starved.
- CPU pressure: the process is spending too much time on compute work, which makes latency rise and can block request handling.
- Memory pressure: the process is holding too much memory or retaining objects too long, which increases GC churn and may lead to OOM restarts.
- API Gateway: the entry layer that routes requests, authenticates traffic, enforces quotas/throttling, and forwards requests to backend services.
- Visibility timeout: the amount of time SQS hides a received message from other consumers so the current consumer can process it before the message becomes visible again.
- DLQ: a dead letter queue where messages that fail repeatedly are sent for inspection instead of being retried forever.
- SLI: the actual metric used to measure a user-visible reliability outcome.
- SLO: the target reliability threshold for an SLI over a period of time.
- SLA: a formal service commitment or contractual guarantee.
- Error budget: the amount of unreliability allowed before an SLO is considered missed.
- Circuit breaker: a safety mechanism that avoids repeated calls to a failing downstream dependency when failure thresholds are exceeded.
- Bulkhead: isolation of resources so one failing component does not consume all the capacity needed by the rest of the system.
- Incident response: the process of detecting, confirming, scoping, mitigating, investigating, verifying, documenting, and preventing recurrence of an outage.

# TASKS 1–2 — AWS

## 1. Lambda

### Concurrency

Definition: Concurrency is the number of Lambda executions running at the same time.

If:

- traffic increases
- execution duration increases
- downstream service becomes slow

then concurrent executions can increase.

Basic relationship:

**Concurrency ≈ requests per second × average duration in seconds**

Example:

100 requests/sec × 2 sec duration ≈ 200 concurrent executions.

### Deeper theory

Concurrency is not just a traffic metric; it is a capacity model. In serverless systems, a slow downstream dependency can increase execution duration without any rise in traffic, which means more execution slots are consumed. This creates a feedback loop: slow dependency → longer runtime → more concurrent executions → throttling → retries → even more downstream pressure.

Timeouts usually reveal deeper system issues rather than a simple Lambda bug. A strong SRE answer traces the request through the dependency graph and checks whether the function is waiting on a database, external API, queue, or resource constraint instead of blaming the Lambda itself.

### Throttling

Definition: Throttling is when Lambda cannot start new executions because the function, account, or regional concurrency limit has been reached.

This is not the same as a function error. It means the system is overloaded or execution time is too high, so new work cannot be admitted. Throttling is one of the clearest signs that the dependency chain is under pressure.

Check:

- ConcurrentExecutions
- Throttles
- Duration
- Errors
- Invocation rate
- Reserved concurrency
- Account/Regional concurrency limits

Possible causes:

- sudden traffic spike
- long-running executions
- reserved concurrency set too low
- downstream dependency becoming slow
- retries increasing traffic

Important chain:

**Dependency slow → Lambda duration ↑ → concurrency ↑ → throttling → retries → even more load**

This is a common cascading-failure pattern.

### Reserved concurrency

Definition: Reserved concurrency is the maximum number of concurrent executions a Lambda function is allowed to run at the same time.

It is a control knob that limits how much capacity a single function can consume. If it is set too low, the function can be throttled even when the rest of the account has available capacity. If it is set too high, a noisy function can consume too much shared concurrency and starve other functions.

### Timeout

Definition: A timeout happens when a Lambda exceeds its configured maximum execution time.

A timeout does not necessarily mean the Lambda code is wrong. More often, it means the function spent too long waiting on a dependency or doing work beyond its expected budget. This can be caused by database latency, an external API, queue processing, large payloads, or CPU/memory pressure.

Investigate:

- recent deployment
- dependency latency
- database queries
- external API calls
- SQS processing
- increased payload size
- CPU/memory pressure

Do not immediately assume the Lambda itself is broken.

# 2. SQS

## Visibility timeout

Definition: Visibility timeout is the length of time SQS hides a message from other consumers after one consumer receives it.

Purpose:

**Give the consumer time to process the message before it becomes visible again.**

If processing takes longer than the visibility timeout:

**message becomes visible → another consumer can receive it → duplicate processing**

Increasing visibility timeout can help when processing legitimately takes longer.

It does NOT provide exactly-once processing.

---

## At-least-once delivery

Definition: At-least-once delivery means a message may be delivered more than once, but it should not be lost.

Standard SQS can deliver a message more than once.

Therefore consumers should be **idempotent**.

Example:

Message:

`paymentId = 123`

Instead of blindly creating another payment record:

- use `paymentId` as an idempotency key
- check whether it was already processed
- use an atomic/conditional database operation where appropriate

---

## SQS backlog

Definition: A queue backlog is a buildup of unprocessed messages waiting in the queue.

A growing queue generally means:

**producers are producing faster than consumers can process.**

Check:

- queue depth
- `ApproximateAgeOfOldestMessage`
- consumer errors
- Lambda throttling
- processing duration
- downstream latency
- DLQ
- traffic increase

Possible mitigation:

- increase consumer capacity
- fix consumer errors
- remove unnecessary retries
- address slow dependencies
- adjust visibility timeout if processing time requires it

### Deeper theory

A backlog is often a signaling problem rather than just a throughput problem. Sometimes the producer rate is stable, but the consumer is slower because of a dependency outage, a deployment regression, or an increase in processing time. That is why queue depth and message age matter together: depth tells you volume, while age tells you lag.

FIFO is useful when message ordering or deduplication matters, but it can also create head-of-line blocking when one message group stalls. A DLQ is not a backup queue; it is a quarantine mechanism for repeatedly failing messages that need operator intervention rather than endless retries.

---

## FIFO vs Standard

### Standard

- very high throughput
- at-least-once delivery
- ordering is not guaranteed
- duplicates possible

### FIFO

- ordering within message groups
- deduplication capabilities
- throughput constraints differ
- message groups can affect parallelism

Important:

A standard SQS message does **not** block the whole queue just because one message fails.

FIFO message groups can introduce ordering/blocking behavior.

---

## DLQ

Definition: A Dead Letter Queue is a queue used for messages that fail repeatedly and are not successfully processed.

Dead Letter Queue = destination for messages that repeatedly fail processing.

Typical flow:

**Main queue → consumer → failure → retry → max receives → DLQ**

DLQ is useful for:

- poison messages
- malformed data
- permanently failing operations
- preventing endless retries

Don't confuse a DLQ with a normal backup/durable processing queue.

# 3. API Gateway

Definition: API Gateway is the entry point for client requests to the backend. It handles routing, request validation, authorization, throttling, and integration with services such as Lambda or EC2.

Know the basic flow:

**Client → API Gateway → Lambda/service → database/dependency**

When API errors increase, determine where the failure is:

- API Gateway?
- Lambda?
- application code?
- database?
- external dependency?

Useful distinction:

### 4xx

Definition: 4xx responses usually mean the request is invalid, unauthorized, malformed, or not allowed.

Usually client/request-related.

### 5xx

Definition: 5xx responses usually mean the server or backend failed while processing the request.

Usually server/infrastructure/application/dependency-related.

But don't blindly assume. Investigate the actual error.

### Deeper theory

API Gateway is often the edge control point, but a 4xx or 5xx spike only tells you there is a problem somewhere in the path. A 5xx could reflect a backend outage, unhandled exception, dependency latency, database failure, or a policy/configuration issue. The real skill is to correlate Gateway metrics with Lambda logs, database health, and downstream dependency metrics before assigning blame.

In production, the question is not just “which component failed?” but “which component is actually responsible for the user-visible failure?” Good debugging follows the request path rather than assuming the first visible layer is the root cause.

Numerical measurements over time.

Rules that trigger when metrics cross defined conditions.

# 5. IAM

Mental model:

**Who/what → can perform → which action → on which resource**

Example:

Lambda execution role allows:

`lambda → sqs:ReceiveMessage → queue-X`

Principle:

**Least privilege**

Only grant the permissions actually required.

Common troubleshooting question:

"Lambda receives AccessDenied."

Check:

- execution role
- attached policies
- resource policy
- resource ARN
- region/account
- explicit deny

### Deeper theory

IAM failures often look like application bugs because the symptom is an outage, but the root cause is usually policy scope or resource mismatch. The mental model is actor → action → resource → conditions, and that matters because a misconfigured policy can block access even when the app code is otherwise healthy.

Good IAM design follows least privilege and clear ownership boundaries. In production incidents, it is common to miss a region mismatch, a wrong ARN, or an explicit deny long before touching the application logic, so policy checks are an essential part of troubleshooting.

# TASKS 3–4 — NODE.JS

# 6. Node.js Event Loop

Definition: The event loop is the mechanism Node.js uses to schedule and process asynchronous work without blocking the main thread.

Node.js is particularly effective for I/O-bound workloads because JavaScript execution uses an event loop and asynchronous APIs.

Typical flow:

**Request → async operation → event loop continues handling other work → callback/promise resumes**

Good workloads:

- HTTP APIs
- database calls
- external APIs
- queues
- I/O-heavy applications

Problem:

**CPU-bound synchronous work blocks the event loop.**

Examples:

- huge loops
- expensive sorting
- massive JSON processing
- expensive regex
- encryption/compression
- image processing

If event-loop blocking occurs:

**one expensive operation → other requests wait → latency increases**

### Deeper theory

Node.js is excellent for I/O-bound workloads because it uses a single-threaded event loop with non-blocking async APIs. That allows one process to handle many concurrent network operations efficiently. The design is excellent for HTTP APIs, queue consumers, external API calls, and database access patterns, as long as those operations are waiting and not doing heavy CPU work.

The problem starts when synchronous CPU-bound work blocks the event loop. Large JSON parsing, expensive regexes, crypto, compression, image processing, or expensive recursive computations can hold the event loop for too long. Once that happens, other requests wait, latency rises, and the system behaves as if it is overloaded even when the actual throughput has not changed.

This is why “Node.js is slow” is often a misleading diagnosis. The real question is whether the process is blocked by CPU work, memory pressure, dependency latency, or event-loop lag. The answer must be supported by runtime metrics, recent deployment history, and sometimes profiling.

Definition: CPU pressure is when the process uses too much CPU time relative to available capacity, causing slower processing and higher latency.

Don't immediately assume "memory leak."

Possible causes:

### CPU-bound code

- large loops
- sorting
- parsing
- JSON serialization
- crypto
- compression
- regex

### Garbage collection

Definition: Garbage collection is the runtime process that frees up memory that is no longer reachable by the application.

If memory usage is high:

**objects retained → GC pressure ↑ → CPU ↑ → latency ↑**

### Traffic

Traffic suddenly increases:

**requests ↑ → CPU ↑**

### Dependency/application changes

A recent deployment may have introduced expensive work.

Investigation:

1. Check traffic
2. Check recent deployments
3. Check CPU
4. Check memory
5. Check latency
6. Check event-loop lag
7. Check errors
8. Profile CPU if necessary

# 8. Node.js Memory Problems

Definition: Memory pressure is when the process is holding onto too much memory or failing to release it, which leads to GC churn, slower performance, and possible OOM crashes.

Symptoms:

- memory continuously increases
- GC activity increases
- latency increases
- OOM errors
- process restarts

Possible causes:

- memory leak
- large objects retained
- unbounded cache
- event listeners not removed
- timers not cleared
- large database/API responses
- loading too much data into memory
- streams not handled correctly

Useful investigation:

- heap snapshots
- memory metrics
- GC behavior
- recent deployments
- object retention
- request/payload sizes

Mental model:

**Memory ↑ → GC pressure ↑ → CPU/latency ↑ → OOM → restart**

### Deeper theory

High CPU does not automatically mean a memory leak. It can be caused by a traffic surge, a recent deployment, a large request payload, a busy dependency path, or expensive synchronous work. This is why a good investigation begins by differentiating between user traffic, deployment risk, CPU-bound code, and GC pressure.

Memory problems usually show up as sustained growth, growing GC activity, rising latency, and eventually out-of-memory crashes or process restarts. Common causes include unbounded caches, retained objects, event listeners not being removed, timers that never clear, or large payloads being kept in memory too long. That is why heap snapshots and retention analysis are so useful in a Node.js incident.

# 9. Async Reliability

Important concepts:

### Timeouts

Definition: A timeout is a maximum wait period for an external call before the request is abandoned.

Never allow an external dependency to hang indefinitely.

### Retries

Definition: Retries are re-attempts of a failed operation, usually used for transient errors.

Useful for transient failures.

But retries can make an incident worse.

Example:

**dependency slow → requests timeout → retry → traffic doubles → dependency gets even more overloaded**

### Exponential backoff

Definition: Exponential backoff is a retry strategy where the delay grows exponentially between attempts.

Increase delay between retries.

Example concept:

`1s → 2s → 4s → 8s`

### Jitter

Definition: Jitter is random variation added to retry timing so many clients do not retry at the same moment.

Add randomness to retry delays so many clients don't retry simultaneously.

### Deeper theory

Async reliability is about controlling failure amplification. A retry can be useful when the failure is transient and the operation is idempotent, but a retry can also create a retry storm if the system is already degraded. This is especially dangerous when a dependency is slow or partially unavailable, because each client retry adds more load and makes the dependency recover slower.

The main patterns are:

- Timeouts: prevent a call from hanging forever
- Retries: recover from transient failures
- Exponential backoff: reduce retry intensity gradually
- Jitter: spread retries out so clients do not hammer the same dependency at the same time
- Circuit breaker: stop calling a failing dependency once failure rate becomes unacceptable
- Bulkhead: isolate resources so one failing subsystem does not consume all capacity

A circuit breaker is not a sign of failure; it is a protective mechanism. It changes the system from “always keep trying” to “fail fast and degrade gracefully,” which is often the difference between a localized issue and a full outage.

---

# 10. Circuit Breaker

Definition: A circuit breaker is a safety mechanism that stops repeated calls to an unhealthy dependency after a threshold of failures is reached.

Purpose:

**Stop repeatedly calling an unhealthy dependency.**

Concept:

**Healthy → failures increase → OPEN → stop requests → recovery period → HALF-OPEN → test → CLOSED**

Useful for protecting your system from cascading failures.

Related concept:

### Bulkhead

Definition: A bulkhead isolates resources so one failing component cannot consume all the capacity needed by the rest of the system.

Isolate resources so one failing component cannot consume everything.

Example:

Notification processing should not consume all resources required by core messaging.

# TASKS 5–6 — OBSERVABILITY & INFRASTRUCTURE TOOLING

# 11. Metrics vs Logs vs Traces

### Metrics

Definition: Metrics are numerical measurements over time that show trends, health, and thresholds.

Answer:

**"What is happening?"**

Examples:

- registration success rate
- API latency
- error rate
- queue depth
- CPU
- Lambda throttles

### Logs

Definition: Logs are detailed records generated by code and systems that show what happened during execution.

Answer:

**"What happened?"**

Examples:

- exception
- request ID
- database error
- business event

### Traces

Definition: Traces show the end-to-end path of a request across multiple services so you can see where it slowed down or failed.

Answer:

**"Where did the request go, and where did it slow/fail?"**

Example:

**Mobile → API Gateway → Lambda → service → database**

Traces are especially useful in distributed systems.

### Deeper theory

The foundation of observability is being able to answer four questions quickly:

1. What is broken?
2. Where is it failing?
3. How severe is the impact?
4. What is the safest immediate mitigation?

Metrics answer the “what is happening?” question. Logs answer the “what happened?” question. Traces answer the “where did the request go and where did it slow or fail?” question. Each is important, but they solve different problems.

For a distributed system, traces are especially valuable because a single request may pass through API Gateway, a Lambda, a database, and a third-party dependency. Without traces, the system may look like a generic latency issue when the actual root cause is a specific call path. Good observability is therefore about connecting the system view to the user journey.

# 12. Good Observability

A healthy infrastructure dashboard isn't enough.

Think in three layers:

### Infrastructure

- CPU
- memory
- Lambda concurrency
- queue depth
- database connections

### Application

- error rate
- latency
- successful requests
- dependency failures

### User journey

- registration success
- message send success
- message delivery success
- verification success
- failed/duplicate/lost messages

The important question is:

**Can the user successfully accomplish the thing they came to do?**

### Deeper theory

A healthy infrastructure dashboard is not enough. The important question is not whether CPU and memory look fine; the important question is whether the user can still complete the service they came to use. That is why reliability should be measured using user-centric SLIs, not only platform metrics.

A good observability stack usually has three layers:

- Infrastructure: CPU, memory, concurrency, queue depth, database connections
- Application: request rate, error rate, latency, dependency errors
- User journey: successful registrations, successful payments, successful message deliveries, repeated failed actions

If infrastructure looks healthy but the user journey fails, the system is still broken. This is the main reason why SRE organizations focus on SLI/SLO design tied to real outcomes.

# 13. SLI / SLO / SLA

This distinction is important.

### SLI

Definition: An SLI is the actual metric used to measure the reliability of a user experience or service.

What you **measure**.

Example:

`successful registrations / registration attempts`

### SLO

Definition: An SLO is the target reliability level for an SLI over a defined time period.

The **target** for that measurement.

Example:

`99.9% successful registrations over 30 days`

### SLA

Definition: An SLA is a contractual or business commitment to a service level, usually agreed with customers or stakeholders.

A contractual/business commitment.

### Deeper theory

SLI, SLO, and SLA are often confused, but they describe different things:

- SLI: the actual measurement of user experience or service reliability
- SLO: the target threshold for that measurement
- SLA: a contractual promise or business commitment

For example, a registration service may define its SLI as successful registrations divided by total registration attempts. An SLO might be 99.9% successful registrations over 30 days. An SLA might be a contractual definition of support guarantees or service availability commitments to customers or partners.

What matters operationally is that SLOs create a shared definition of acceptable failure. They are not just engineering goals; they are decision tools. They help teams decide whether a feature rollout is safe, whether the error budget is running low, and how much risk is acceptable in a given period.

---

# 14. Error Budget

Definition: An error budget is the allowed amount of unreliability before an SLO is considered missed.

If SLO = 99.9%:

Error budget = **0.1%**

The error budget represents how much unreliability is allowed before the SLO is missed.

Important:

An exhausted error budget does not automatically mean:

**"STOP ALL DEVELOPMENT."**

Instead:

- understand why the budget was consumed
- assess current risk
- consider deployment safeguards
- use canaries/feature flags where appropriate
- prioritize reliability work if necessary

### Deeper theory

An error budget is the amount of unreliability permitted without violating the SLO. If the SLO is 99.9%, then the error budget is 0.1%. This tells the team how much failure is acceptable over a measurement window.

The important mindset is that an error budget is not a license to ignore reliability. It is a decision-making signal. If the team is consuming the error budget too quickly, that means reliability is worse than expected and more caution may be needed around deployments, changes, or riskier features.

A mature team uses the budget to decide:

- whether to slow releases
- whether to prioritize reliability work
- whether a canary or feature flag is needed
- whether an incident should trigger a rollback or safe mitigation

This is why service reliability is as much about operational decisions as it is about technical metrics.

# TASKS 7–8 — INCIDENT RESPONSE

# 18. Incident Response Framework

Definition: Incident response is the process of detecting, confirming, mitigating, investigating, and recovering from a production issue.

Memorize this mental sequence:

**1. Detect**

What triggered the incident?

### Deeper theory

Incident response is a combination of technical diagnosis and decision-making under pressure. A strong response is not only “fix the root cause,” it is also “restore the user experience safely and quickly while gathering enough evidence to prevent recurrence.”

The reliable framework is:

Detect → Confirm → Assess impact → Scope → Mitigate → Investigate → Verify → Document → Prevent

The first principle is to prioritize user impact. If registration is failing globally, that takes precedence over a small rise in a non-critical Lambda error rate. A second principle is to check whether multiple alerts are symptoms of the same underlying failure. Otherwise, the team may waste time chasing disconnected signals.

Another important distinction is mitigation versus root cause:

- Mitigation reduces current impact quickly
- Root cause prevents recurrence

During an incident, the priority is usually to restore service first, then move into root-cause investigation and systemic improvement. This is why rollback, traffic reduction, retry tuning, feature flag disabling, and circuit breakers are valuable tools.

**2. Confirm**

Is this a real problem or a false positive?

**3. Assess impact**

Who is affected?

- percentage of users
- global vs regional
- one endpoint vs entire service
- data loss?
- degraded performance?
- business impact?

**4. Scope**

Find the boundaries.

**5. Mitigate**

Restore service as quickly and safely as possible.

**6. Investigate**

Find the root/contributing causes.

**7. Verify**

Confirm recovery using metrics, logs and user-facing SLIs.

**8. Document**

Record timeline, actions and findings.

**9. Prevent recurrence**

Fix code, architecture, monitoring, runbooks or process.

---

# 19. The Best Incident Answer Structure

For subjective questions:

**Impact → Hypothesis → Investigation → Mitigation → Verification → Prevention**

Example structure:

> The first thing I would do is confirm the impact and scope. I'd check the relevant user-facing metric, then correlate it with application and infrastructure metrics. I'd look for recent deployments or dependency failures. If I identified a recent deployment as the likely cause, I'd consider rollback as the fastest mitigation. After recovery, I'd verify that the user-facing metric returned to normal and then investigate the underlying cause and document the incident.

This is a framework for thinking — your actual assessment answer should be written in your own words.

# 20. Incident Prioritization

Prioritize based primarily on:

**user/business impact + severity + scope**

Example:

1. Registration success falls globally from 99.9% to 92%
2. Notifications delayed
3. Small increase in non-critical Lambda errors

The first issue affects a critical user journey and a large population.

Also ask:

**Could these alerts be symptoms of the same underlying incident?**

Don't investigate every alert independently if they may have a common cause.

# 21. Mitigation vs Root Cause

Very important distinction.

### Mitigation

Restores/reduces impact quickly.

Examples:

- rollback
- disable feature
- increase capacity
- stop traffic to unhealthy dependency
- activate circuit breaker
- scale consumers

### Root-cause fix

Prevents the underlying problem from happening again.

Examples:

- code fix
- architecture change
- better timeout
- idempotency
- capacity planning
- improved monitoring

During an incident:

**Restore first. Investigate deeply second.**

---

# 22. Postmortem

A useful postmortem should focus on learning, not blame.

Include:

- incident summary
- impact
- timeline
- detection
- mitigation
- root/contributing causes
- what went well
- what didn't
- action items
- owners
- monitoring/process improvements

Avoid treating "human error" as the complete explanation.

Ask:

**Why was the system/process vulnerable to that error?**

# 23. Your Real Incident Story

You have a strong production example involving carrier shipment updates.

Mental outline:

**Problem**

Carrier sent updates for shipment IDs that no longer existed in your database.

**Investigation**

- checked CloudWatch/Lambda logs
- checked database
- checked subscription/creation history
- checked recent activity
- determined there was no active shipment
- investigated lifecycle behavior

**Finding**

Your system removed shipment tracking after 90 days, while the external carrier could continue sending updates.

**Root cause**

The unsubscribe operation happened too late relative to internal housekeeping.

**Fix**

Changed the unsubscribe timing to occur 3 days before internal cleanup.

**Lesson**

When integrating with external systems:

**consider the complete lifecycle of data on both sides.**

**broken user experience.**

That's why product/user-centric SLIs matter.

# THE CORE ANSWER FRAMEWORK

For almost every SRE scenario, think:

**1. Impact**
What is broken and who is affected?

**2. Scope**
Global? Regional? One endpoint? One dependency?

**3. Evidence**
Metrics → logs → traces.

**4. Hypothesis**
What changed or could explain the symptoms?

**5. Mitigation**
What can safely reduce impact now?

**6. Verification**
Did the user-facing metric recover?

**7. Prevention**
What should change so it doesn't happen again?

That framework should be your default mental model throughout the assessment.
